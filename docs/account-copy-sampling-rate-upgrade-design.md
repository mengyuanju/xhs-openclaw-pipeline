# 文案抽检比例按账号配置升级方案

## 1. 结论

保留“生产配置”中的文案抽检开关和比例，将现有统一比例调整为**默认比例**；在“用户管理”中为每个账号增加可空的“文案抽检比例覆盖值”。普通文案随机抽检按以下顺序解析：

1. 质检打回后的强制复检固定为 100%，不受任何普通抽检配置影响。
2. 生产配置关闭“启用文案抽检”时，所有账号的普通随机抽检都关闭；账号覆盖值保留，但暂不生效。
3. 生产配置开启时，账号存在覆盖值则使用账号值。
4. 账号未配置覆盖值时，继承生产配置中的默认比例。

账号口径沿用当前系统的 `copy_approval_events.approved_by_account_id`，即**最终人工通过文案的账号**。它不是任务创建人、任务负责人，也不是执行抽检的质检员账号。

本方案只调整文案随机抽检比例。图片抽检比例、盲评开关、质检员整批打回权限、强制复检规则均保持现状。

## 2. 当前系统基线

当前实现已经具备按最终审核账号独立累计的基础：

- `workflow_quality_settings.copy_sampling_rate_bps` 保存唯一的全局文案抽检比例，精度为万分之一，页面用 0–100% 展示。
- `attemptAutomaticCopySamplingFreeze` 先按最终审核账号分组，再为每个账号独立规划冻结批次。
- `copy_sampling_remainders` 按 `final_approver_account_id` 保存余数，使 20% 能在长期接近“每 5 条抽 1 条”，而不是对每个小批次简单向上取整。
- `copy_sampling_freezes` 已保存实际比例、全局策略版本、最终审核账号、冻结前后余数、算法版本和快照哈希；冻结后成员不可因配置变化而重算。
- 用户管理目前只保存文案审核、文案质检、图片质检三个布尔权限，没有账号级抽检比例。

因此，本次升级不需要重写抽样算法。核心改动是：在每个账号分组进入 `planCopyQualityChunk` 和 `createFreeze` 前，解析并冻结该账号的有效比例。

## 3. 产品规则

### 3.1 配置优先级

| 场景 | 有效抽检策略 | 比例来源 |
| --- | --- | --- |
| 质检打回后的强制复检 | 100% | `MANDATORY_RECHECK` |
| 生产配置关闭文案抽检 | 普通随机抽检关闭 | `GLOBAL_DISABLED` |
| 生产配置开启，账号覆盖值为 0–100% | 使用账号覆盖值 | `ACCOUNT_OVERRIDE` |
| 生产配置开启，账号覆盖值为 `null` | 使用生产配置默认值 | `GLOBAL_DEFAULT` |
| 历史最终审核账号已删除或无法读取 | 使用生产配置默认值 | `GLOBAL_DEFAULT` |

这里的“用户管理优先级更高”是指：**全局开关开启后，账号覆盖比例优先于生产配置默认比例**。全局开关继续作为管理员紧急停止普通抽检的总开关，避免关闭抽检时仍有部分账号继续进入抽检。

### 3.2 `null` 与 `0%` 必须区分

- `null`：继承生产配置默认比例。
- `0`：账号明确覆盖为 0%。

为保持当前系统语义，开启普通抽检时，0% 在批次未闭合阶段不会触发比例抽检，但批次关闭或等待超过 30 分钟后，非空尾批仍保底抽 1 条。它不是“免检”。如果以后需要真正的账号免检，应新增显式的“免抽检”策略，不应复用 0%。

### 3.3 生效时间

- 有效比例在**创建抽检冻结快照时**读取，与当前生产配置的生效时点一致。
- 已冻结批次继续使用冻结时保存的比例和成员，不重算、不增删样本。
- 已人工通过但尚未冻结的文案，使用冻结时最新的账号配置。
- 修改账号比例不清空 `copy_sampling_remainders`。余数代表此前尚未形成完整样本的累计份额，继续保留可避免频繁改配造成系统性少抽或重复抽检。
- 账号比例变更只增加用户业务版本，不增加 `credential_version`，不应导致用户掉线。

### 3.4 示例

假设生产配置已开启，默认比例为 20%：

| 最终审核账号 | 用户管理配置 | 有效比例 | 典型效果 |
| --- | --- | --- | --- |
| A | 单独配置 50% | 50% | 长期约每 2 条抽 1 条 |
| B | 继承生产配置 | 20% | 长期约每 5 条抽 1 条 |
| C | 单独配置 0% | 0% | 平时不按比例触发，结批/超时的非空尾批保底 1 条 |
| D | 单独配置 100% | 100% | 每条普通审核结果均进入抽检 |

## 4. 数据模型

实现使用迁移 `0084_account_copy_sampling_rate.sql`（0081–0083 已用于其他升级）。

### 4.1 当前账号配置

在 `app_users` 增加：

```sql
ALTER TABLE app_users
  ADD COLUMN copy_sampling_rate_bps_override integer
  CHECK (
    copy_sampling_rate_bps_override IS NULL
    OR copy_sampling_rate_bps_override BETWEEN 0 AND 10000
  );
```

不做历史回填，所有已有账号默认为 `null`，上线后继续继承当前全局比例，行为不变。

字段应保存在账号上，而不是文案审核权限表或自动派单池中，原因是抽检归因使用稳定的 `app_users.id`，并且管理员、质检员、普通作业员都可能成为最终人工通过人。

### 4.2 配置变更审计

新增独立审计表 `account_copy_sampling_policy_events`：

```sql
CREATE TABLE account_copy_sampling_policy_events (
  id bigserial PRIMARY KEY,
  account_id bigint NOT NULL,
  actor_account_id bigint,
  actor_username varchar(50) NOT NULL,
  previous_rate_bps_override integer,
  rate_bps_override integer,
  created_at timestamptz NOT NULL DEFAULT now(),
  CHECK (previous_rate_bps_override IS NULL OR previous_rate_bps_override BETWEEN 0 AND 10000),
  CHECK (rate_bps_override IS NULL OR rate_bps_override BETWEEN 0 AND 10000)
);
```

`account_id` 和操作者信息保存历史快照，不对 `app_users` 建删除级联外键，避免账号删除后丢失配置审计。仅当覆盖值真实变化时写入事件。

不建议把比例直接塞入现有 `copy_quality_permission_events.permissions` JSON。比例是策略配置而非登录/操作权限，独立表更便于审计和统计，也避免改变既有权限事件的解释。

### 4.3 冻结快照

`copy_sampling_freezes.rate_bps` 已能保存实际生效比例，继续作为历史权威值。为说明其来源，增加：

```sql
ALTER TABLE copy_sampling_freezes
  ADD COLUMN rate_source varchar(30) NOT NULL DEFAULT 'GLOBAL_DEFAULT'
    CHECK (rate_source IN ('GLOBAL_DEFAULT', 'ACCOUNT_OVERRIDE', 'MANDATORY_RECHECK')),
  ADD COLUMN account_policy_version bigint;
```

- 现有 `policy_version` 继续表示全局 `workflow_quality_settings.version`。
- `account_policy_version` 保存冻结时读取到的 `app_users.version`；历史账号不存在时为 `null`。
- 强制复检保存 `rate_bps = 10000`、`rate_source = 'MANDATORY_RECHECK'`。
- `FREEZE` 事件的 `details` 同步保存 `effectiveRateBps`、`rateSource`、`globalPolicyVersion` 和 `accountPolicyVersion`，便于无需拼接当前账号表即可审计。

## 5. 服务端设计

### 5.1 统一解析函数

新增纯函数，所有普通文案冻结只从这里取得有效策略：

```js
resolveEffectiveCopySamplingPolicy({
  globalEnabled,
  globalRateBps,
  globalPolicyVersion,
  accountRateBpsOverride,
  accountVersion,
})
```

返回：

```js
{
  enabled,
  rateBps,
  rateSource,
  globalPolicyVersion,
  accountPolicyVersion,
}
```

不要在页面、API 和冻结流程中分别复制优先级判断。

### 5.2 自动冻结流程

调整 `attemptAutomaticCopySamplingFreeze`：

1. 继续锁定生产批次和待冻结任务。
2. 查询待冻结任务时，按 `approval.approved_by_account_id` 左连接 `app_users`，一次性取得账号覆盖值和账号版本。
3. 继续按最终审核账号分组。
4. 全局开关关闭时，沿用现有逻辑将普通任务直接放行到 `IMAGE_QUEUED`。
5. 对每个账号组解析有效比例，用该比例调用 `planCopyQualityChunk`。
6. 将有效策略传给 `createFreeze`；`selectStratifiedCopySample`、冻结表和 `FREEZE` 事件全部写入同一个有效比例，禁止一处用账号比例、另一处仍写全局比例。
7. `copy_sampling_remainders` 仍按账号 ID 独立读写，算法与锁定顺序保持不变。

账号查询必须使用 `LEFT JOIN`。如果最终审核账号后来被删除，不能阻塞生产批次，应按全局默认比例处理并在冻结来源中记录为 `GLOBAL_DEFAULT`。

### 5.3 强制复检与其他流程

- `routeManualCopyApproval` 中的强制复检分支保持 100%，不读取账号覆盖值。
- 全局盲评开关仍在冻结时保存，不做账号级覆盖。
- 质检员整批打回权限仍在操作时实时校验，不做账号级比例联动。
- 当前按最终审核账号统计正确率的逻辑不变。
- 幂等请求、快照哈希和成员不可变规则不变；快照哈希中应包含最终有效比例，现有算法已经具备该项。

### 5.4 用户接口

`GET /v1/users` 的每个用户增加：

```json
{
  "copySamplingRateBpsOverride": null
}
```

`POST /v1/users` 和 `PATCH /v1/users/:userId` 接受同名字段：

- `null`：继承生产配置。
- `0`–`10000` 的整数：账号覆盖值。
- 创建账号未传时默认为 `null`。
- 更新账号未传时保留当前值，以兼容旧版 Web；新版 Web 切换“继承”时必须显式发送 `null`。
- 非整数、越界值或字符串由中心服务拒绝，不能只依赖前端校验。

账号更新继续使用 `expectedVersion` 做乐观并发控制。比例变化使 `app_users.version + 1` 并写审计事件，但不使 `credential_version` 增加。

### 5.5 能力版本与混合部署保护

中心 `/health` 将 `copySamplingVersion` 从 1 提升到 2。新版 Web 在该版本小于 2 或无法确认时，不展示可保存的账号比例控件，并明确提示“中心服务尚未支持账号级比例”。

不能让新版 Web 把字段发送给旧中心后仍提示保存成功，因为旧版 `createUser/updateUser` 会忽略未知字段，造成管理员误以为配置已生效。

## 6. 管理端页面设计

### 6.1 用户管理

在新增/编辑用户弹窗的权限区域增加“文案抽检比例”：

- 模式一：`继承生产配置（当前默认 20%）`。
- 模式二：`单独配置`，输入 0–100%，步进 0.01%。
- 当生产配置总开关关闭时显示：“普通文案抽检当前全局关闭，账号配置会保留并在重新开启后生效。”
- 当输入 0% 时显示：“0% 仍会在结批或等待超时后对非空尾批保底抽 1 条。”
- 文案审核权限关闭时仍保留已存覆盖值，但标记“当前不会产生新的最终审核结果”；重新开启权限后无需重新录入。

用户列表增加“文案抽检”列或摘要标签：

- `继承 · 20%`
- `单独 · 50%`
- `单独 · 0%（尾批保底）`
- 全局关闭时统一增加 `暂不生效` 状态，不把覆盖值误显示为当前正在执行。

### 6.2 生产配置

将现有“抽检比例”文案改为“默认抽检比例”，并补充说明：

> 未在用户管理中单独配置的最终审核账号继承此比例；用户管理中的账号比例优先。关闭文案抽检会暂停所有账号的普通随机抽检，强制复检不受影响。

盲评和整批打回开关不需要移动到用户管理。

### 6.3 管理员追溯

管理员查看抽检冻结详情时，应显示：

- 最终审核账号；
- 实际抽检比例；
- 来源是“账号单独配置”还是“生产配置默认值”；
- 冻结时间；
- 全局策略版本和账号版本。

非管理员盲评视图不能因新增字段泄露上游账号身份或策略来源。

## 7. 并发、一致性与异常边界

- 用户配置更新与冻结并发时，以冻结事务实际读取并写入快照的版本为准。更新成功后新开始的冻结必须读取新值；已写入冻结快照的批次不重算。
- 同一个账号组一次冻结只能使用一个有效比例。账号配置应在进入分组循环前一次性读取，不能每处理一个块重新查询，避免同一轮出现两个比例。
- 全局配置和账号配置分别使用现有版本号防止管理员覆盖彼此的修改；冻结快照同时保存两侧版本。
- 账号停用、角色变化或文案审核权限关闭不会修改已有冻结，只影响以后能否产生新的人工通过记录。
- 账号删除后已有抽检项、审批事件和审计事件继续保留稳定账号 ID；尚未冻结的历史审批按全局默认比例兜底。
- 比例变化不回溯修改正确率，不改变已经形成的质检结论。

## 8. 发布与迁移

推荐按以下顺序发布：

1. 备份中心 PostgreSQL，发布包含 `0084` 迁移和 `copySamplingVersion = 2` 的中心服务。
2. 验证所有已有账号的覆盖值为 `null`，全局配置和历史抽检行为未变化。
3. 发布新版 Web，确认能力版本后开放用户管理控件。
4. 先选择一个测试账号配置非默认比例，使用新生产批次验证冻结快照、比例来源、余数和质检队列。
5. 再由管理员逐账号配置正式比例。

迁移不回填账号覆盖值、不重算历史冻结、不清空余数，因此回滚 Web 不影响中心行为。若需回滚中心代码，应保留新增列和表，不执行破坏性降级；旧代码会继续使用全局比例。

## 9. 测试与验收

### 9.1 单元测试

- 全局关闭时账号覆盖不生效。
- 全局开启且覆盖为 `null` 时使用默认比例。
- 覆盖值 0、1、9999、10000 正确解析；越界和非整数被拒绝。
- 账号记录缺失时回退全局默认值。
- 比例来源和两个版本号正确返回。
- 现有 `planCopyQualityChunk` 余数、结批保底和 100% 全检用例保持通过。

### 9.2 数据库与服务测试

- 迁移后旧账号全部继承全局配置，现有行为不变。
- 创建、更新、清空覆盖值均正确；旧客户端缺字段时不清空已有值。
- `expectedVersion` 冲突被拒绝。
- 只改比例不会增加 `credential_version`，不会使现有会话失效。
- 每次真实变化产生一条审计事件；重复提交相同值不产生伪变更事件。
- 同一生产批次内，账号 A 使用 50%、账号 B 继承 20%，分别生成冻结和余数。
- 修改比例后仅未冻结任务采用新值，已有冻结的 `rate_bps`、成员和快照哈希不变。
- 全局关闭时普通任务直接放行；强制复检仍为 100%。
- 覆盖 0% 的非空尾批在结批或超时后仍保底 1 条。
- 删除最终审核账号后，尚未冻结任务能按全局默认值继续处理。
- 盲评响应不新增账号身份或比例来源字段。

### 9.3 页面验收

- 用户弹窗能在“继承”和“单独配置”之间切换，0% 与空值不会混淆。
- 用户列表准确显示来源、有效比例和全局关闭状态。
- 生产配置页面明确显示其比例为默认值。
- 中心能力版本不足时账号比例控件不可保存，不出现假成功。
- 两名管理员同时编辑同一账号时，后提交的旧版本得到冲突提示并要求刷新。

## 10. 建议实施拆分

1. 数据库迁移、有效策略解析函数和审计表。
2. 用户 CRUD/API、能力版本和服务端测试。
3. 自动冻结按账号读取有效比例、冻结来源快照和回归测试。
4. 用户管理与生产配置页面改造、混合部署保护。
5. 管理员冻结详情展示、文档与端到端验收。

以上拆分保证前三步先建立中心端权威行为，页面只负责编辑和展示，抽检比例不会由客户端计算后直接决定。

实现补充：账号比例只通过管理员用户管理接口返回，不添加到登录或个人资料响应。Web 代理在请求包含账号比例字段（包括 `null`、`0`）时再次检查中心 V2 能力；旧客户端不传字段仍可维护用户资料。历史强制复检轮次只补充来源标签，不改动实际比例、冻结成员或哈希。尾批保底可能使小批次的实际抽检占比高于配置比例。
