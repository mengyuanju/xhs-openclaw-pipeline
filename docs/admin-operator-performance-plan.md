# 管理员作业人员质量与效率评估修改方案

状态：已完成管理员人员质量与效率功能实现及本地验证，尚未部署生产。以下保留设计依据；实际交付范围、口径细化和升级步骤见 [实现说明](./admin-operator-performance.md)。

## 1. 目标与设计结论

管理员需要回答四个问题：每个人完成了多少、提交质量怎样、哪一段处理慢、返修是否有效。建议把现有 `/workbench-statistics` 扩展为“团队总览 + 人员表现 + 人员详情”，质量按实际提交人归属，待办按当前负责人归属。

核心指标为文案/图片首轮质检通过率、阶段提交量、最终放行量、返修轮次、人工待办周转时长。文案和图片分别比较，机器生成、排队、质检等待单独展示。

第一版不设置笼统的综合绩效分。用同阶段、同任务类型、同抽检政策的对比，结合样本数和任务明细作判断。高通过率且样本很少、高产量但大量免检，都不能直接判断为高绩效。

## 2. 当前实现与需要修正的问题

| 当前实现 | 影响 | 修改方向 |
| --- | --- | --- |
| `admin-statistics.tsx` 显示团队卡片、前六位负责人和紧凑效率区 | 缺少所有人员的完整质量与效率比较 | 接入人员表现表和人员详情 |
| `people-table.tsx` 已有“首评通过率”，但当前管理员页未引用 | 已有表格不等于管理员已经能看到人员通过率 | 复用表格交互，重构数据契约 |
| `summarizeEfficiency()` 以人工首评分数大于 2 计算 `peopleQuality`，混合文案与图片 | 衡量的是初始内容评分，不能代表作业员提交后被质检认可；文案 2.5 分也不代表原稿可以直接通过 | 评分移至“原稿与模型质量”；人员指标读取实际质检事件 |
| `resolveWorkOwner()` 按当前负责人归属，完成量依赖当前 `REVIEWED` 状态和 `imageReviewedAt` | 改派会转移历史成绩；重做会使历史完成量变化 | 历史采用提交/结论/放行事件，当前待办保留当前归属 |
| 文案/图片平均耗时来自执行记录，“交付耗时”为创建到当前审核完成 | 机器性能与流程等待混入人员效率；尚不是下载或确认交付耗时 | 改名并拆分时段，交付确认沿用批次事件单独统计 |
| “一次完成率”来自执行是否重做 | 不能表达人工首轮质检通过 | 改为“未发生同阶段重做的作业占比”，保留在生成分析中 |
| 管理员统计在 Web 端分页读取任务，再逐条读取详情 | 数据量增大时慢，刷新过程中存在多个读取时点 | 人员报表转为 PostgreSQL 中心聚合，按需读取明细 |
| 个人统计已读取提交账号、抽检结论及返修事实 | 可以复用真实数据与口径 | 抽出共享事实层，个人/管理员共用指标规则 |

主要依据：`app/workbench-statistics/{admin-statistics,people-table,efficiency-panel}.tsx`、`src/web-statistics/{summary,service}.mjs`、`server/src/personal-workspace.mjs`、`src/personal-workspace.mjs`。

## 3. 指标定义

### 3.1 质量指标

**文案首轮质检通过率 = 首轮随机抽检通过数 / 已出有效结论的首轮随机抽检数。** 图片采用相同公式，独立计算。

“首轮”沿用个人统计的业务含义：对任务某阶段，在完整历史中确定最早一次被随机抽中的质检项；再取该项首个有效人工结论。先确定首轮，再应用日期、人员筛选，不能先截取本月再找第一次。该指标是“首轮抽检表现”，并非所有任务的首次提交成功率。

- 样本单位为任务 × 阶段；主指标每阶段每任务最多一个样本。多次点击、重放请求、修改版本不会增加首轮样本。
- 分子使用实际 `PASS`，分母使用实际 `PASS` 或 `RETURN_SINGLE`；以追加式事件优先，历史回退状态必须有可靠审核时间和归属。
- 未抽中、等待结论、免检、异常放行、管理员快捷直放、强制复检不进入首轮分母；分别显示数量。
- 管理员正常执行质检可以作为正常样本；明确的直放和自检单列，不与独立质检混算。历史无法判断的情况列为口径不完整。现有 `directAdminApproval` 及直放审计表可识别部分记录。
- 首轮已被直放或无结论失效时，不拿后续轮次顶替首轮。已出结论后变为 `SUPERSEDED`，原首轮结论仍保留。
- 整批退回影响的未实际审核成员不逐条算作个人首轮失败，独立显示“批次退回影响”；实际单条审核失败仍计失败。
- 缺少身份、时间、版本链以及明确为模拟的数据单列排除；历史来源不明显示“来源未确认”，不得伪装成已确认真实样本。
- `0/0` 返回 `null`，界面显示“— / 无样本”。率必须同时展示分子、分母，例如 `90%（18/20）`。

| 补充指标 | 定义与用途 |
| --- | --- |
| 已审样本退回率 | 同一首轮样本集合中的退回数 / 有效结论数；与首轮通过率互补 |
| 复检通过率 | 有效强制复检通过轮次 / 已出结论的强制复检轮次；不覆盖首轮成绩 |
| 一次返修通过率 | 每条返修链首次复检通过数 / 已出结论的首次复检数；未返修、未结论单列 |
| 退回作业数、退回次数 | 期间实际退回的去重任务数、事件次数；按单条质检/终审返工/批次影响区分，不能直接除以另一批期间提交量当退回率 |
| 重复返修作业数 | 在所选期发生第二次及以上真实退回的去重任务数；轮次依据完整历史 |
| 抽检覆盖率 | 期间首次阶段提交集合中，至报表时点已被首轮随机抽中的任务数 / 同集合具备普通抽检资格的任务数；另示实际完成审核比例 |
| 质检原因分布 | 按退回事件及原因代码统计，同一事件同一原因去重，多原因占比允许合计超过 100%并注明 |

质量默认按“结论发生日”查询，覆盖率采用“提交发生日”的固定集合，页面明确两种时间口径。详情可切换到“期间提交集合，截至某时点的处理结果”；未结论单列，后续结论可能改变该集合的结果。

首轮样本数小于 20 时建议显示“样本较少”，第一版作为展示规则，不当作统计显著性结论。按通过率排序时始终显示样本数，不把少量样本自动评为优秀。

### 3.2 产量指标

| 指标 | 计数与归属 |
| --- | --- |
| 文案提交量 | 期间人工文案提交事件按任务、操作账号去重；返修重复提交不增加同人同阶段任务数，另记提交次数 |
| 图片提交量 | 期间图片初审提交事件按任务、操作账号去重，不能称为已质检通过 |
| 参与完成作业数 | 个人期间文案/图片提交任务的并集；保留阶段贡献 |
| 首次最终放行量 | 任务历史第一次图片阶段有效放行发生在期间的去重任务数，归属对应图片提交账号；区分抽检通过、普通免检、人工例外放行 |
| 再次放行/修订交付量 | 已首次放行任务的新版本再次有效放行，单列，不重复扩大首次完成量 |
| 当前有效完成量 | 当前有效版本处于已放行状态的任务数，属于现状快照，返工后可以减少 |
| 已确认交付量 | 沿用交付批次确认记录，按期间去重任务/有效版本统计，批次另计；包装或确认人不自动获得前序文案和图片成绩 |
| 当前待办/待返修/超时 | 按当前负责人和可操作阶段统计，独立于历史日期范围 |

团队去重作业数不等于所有人的参与数相加：A 提交文案、B 提交图片，团队是 1 个任务，两人各有 1 个阶段贡献。不同日期反复提交同一任务，期间去重数也不等于每日去重数之和；趋势与期间汇总分别计算并注明。

不使用“期间完成量 / 期间分配量”作为通过率；跨期任务会令这个比值超过 100%。如保留，只命名为流入流出比。团队通过率用总通过样本 / 总已审样本计算，不平均每个人的百分比。

### 3.3 时间与效率指标

| 指标 | 起止与规则 |
| --- | --- |
| 文案人工待办周转时长 | 同一次文案提交周期内，该账号负责且文案可人工处理的所有时段之和，结束于提交/转派/取消等实际事件 |
| 图片人工待办周转时长 | 同一次图片提交周期内，该账号负责且图片可人工处理的时段之和；后台编辑结果需确认时重新开始可操作时段 |
| 返修总周转时长 | 一次明确退回到对应阶段下一次有效重提的自然时间；必须沿返修链匹配，不能误配另一阶段最近一次退回 |
| 返修人工待办周转时长 | 上述周期中本人负责且可人工修改/确认的时段之和 |
| 质检等待时长 | 提交后等待抽检、分配、审核结论的时段；批次等待单列 |
| 机器排队/执行时长 | 由队列与执行事件计算；重试、恢复、并发区间按实际含义去重 |
| 端到端完成时长 | 创建到首次最终放行，作为流程指标；不直接作为个人处理速度 |
| 当前待办等待时长 | 当前可操作阶段/当前归属开始到现在；保存草稿、心跳、普通同阶段改版不重置 |

时间统一展示中位数、P90 和样本数，平均值作为辅助。默认按结束事件发生日归入期间，起点可以早于期间；当前未结束作业单列“仍在处理/等待”，防止只看已完成的快任务。

**人工待办周转时长仍是自然经过时间，不是真实操作工时。** 第一版不推算“每小时产量”，不把打开页面、最后活动时间或机器耗时当员工工时。多人或多任务并行的时长也不能相加当工时。若以后要实际工时，另行设计明确的开始/暂停/结束及多窗口去重机制。

非工作时间暂不扣除；如有明确班次，再增加工作日历并显示独立指标。超时阈值应按阶段配置，未确定前可沿用 24 小时作跟进提醒，不作为迟到或绩效判定。

## 4. 人员归属与特殊情况

1. 当前待办使用当前负责人；历史文案贡献使用 `approved_by_account_id`，图片使用 `submitted_by_account_id`。审核人是判定者，不能拿 `reviewed_by_account_id` 给提交人记产量。
2. 首轮质量归提交该版本的人。A 提交被退回，B 接手修好：A 保留首轮失败，B 获得返修提交与复检表现；不会给 B 虚构首轮失败。
3. 改派在时间线上关闭原负责人的时段，并开始新负责人的时段；旧耗时不转移。提交周期总历时和个人分段耗时分别展示。
4. 图片质检要求返修文案或图文时，保留“判定来源阶段 IMAGE”及“整改目标 COPY/IMAGE/BOTH”两个维度。双阶段返修在任务数中去重，阶段工作量可各计一次，不能重复扣质量样本。
5. 管理员代作按实际操作人记贡献，不自动记给名义负责人；详情同时显示负责人、提交人、质检人。
6. 账号采用稳定账号 ID，另存发生时的用户名/显示名/角色快照。改名、停用、角色调整不能转移旧成绩；删除后重建同名账号不能继承。旧记录无法可靠匹配则列“历史身份未确认”。
7. 质量失败后废弃仍保留已有失败；取消未审核任务不增加质量失败样本，另列取消原因与数量。批次退回影响不得伪装成逐条质检失败。
8. 版本过期影响当前可交付状态，不删除已发生的提交与审核事实。需要纠错时追加更正记录和原因，不静默覆盖已出报表的证据。

## 5. 页面与交互

沿用管理员现有入口与组件体系；人员表现建议默认近 30 天，支持今日、近 7 天、自定义 1–366 天。

页面布局：筛选条 → 团队概况 → 人员表现表 → 趋势/原因分析。原机器生成效率放入独立“生成与流程”页签。

- 筛选：日期、人员、实际作业阶段、任务来源/生产批次、任务类型、抽检政策；用户角色仅为辅助，支持实际参与文案或图片的 USER/REVIEWER。历史角色有快照才提供发生时角色筛选；旧数据不从当前角色反推。
- 团队卡片：阶段提交量、首次最终放行量、文案/图片首轮通过率、真实退回量、当前待返修、长等待作业。卡片注明“期间事件”或“当前状态”。
- 人员表固定姓名/账号，默认列展示文案提交、图片提交、首次放行、文案首轮通过率、图片首轮通过率、退回/重复返修、文案/图片周转中位数、当前待办。P90、复检、覆盖率等置于可选列或展开区。
- 所有率显示分子/分母；缺数据、无样本、未完成审核、样本不足采用不同文案。人员表支持服务端分页、搜索、排序；未达到样本门槛时标识提示。
- 点击人员打开详情抽屉：产量与质量趋势、两个阶段耗时分布、主要退回原因、批次影响、可分页任务清单。
- 点击指标直接进入对应分子/分母的任务清单，携带人员、阶段、日期、口径版本、报表时点和明细类型；不可跳到“当前分配列表”代替历史依据。
- 单任务显示提交版本、提交人、首次/复检结论、退回原因、负责人变更、各时段耗时和交付状态；历史事实与当前状态并列。
- 趋势用日期 × 通过率/样本数和完成量；按阶段、批次、图片页数等实际可得难度因素比较。不同抽样策略分组显示，避免混合样本误导。
- 导出与当前筛选一致的 CSV，包含分子分母、时区、生成时点、排除数、口径版本；大结果使用有上限的分页/流式读取并防止公式注入。
- 移动端保留人员、主要质量与产量列，耗时和其他字段展开；加载错误保留上次成功数据并标明时间，不能展示为 0。

## 6. 数据与后端设计

### 6.1 复用现有事实

报表以 PostgreSQL 控制面为事实源，不从本地 SQLite 队列另建人员成绩。

| 事实 | 现有来源 |
| --- | --- |
| 人工文案提交 | `copy_approval_events`、`copy_revisions` |
| 图片初审提交 | `image_approval_events` |
| 随机抽检/复检 | `copy_sampling_items/events`、`image_sampling_items/events` |
| 抽检政策与批次 | 文案/图片 sampling freezes、production batches |
| 终审返工与历史评分 | `human_quality_assessments`；只在对应指标使用 |
| 现有分配与部分阶段起点 | `task_assignment_events`、`review_queue_assignment_events`、`copy_quality_queue_events` |
| 当前等待起点 | `tasks.personal_stage_entered_at`，只能说明当前阶段 |
| 机器与后台任务 | 执行记录、图片编辑请求、规划生成记录 |
| 交付 | `delivery_entries`、交付批次及确认事件 |

把现有个人统计中的事件归一化抽为共享模块，但不能原样复制后只去掉 `account_id=$1`：必须补齐管理员直放/自检识别、批次影响、跨阶段返修匹配、历史身份与分母排除。个人统计与管理员选定同一个人、阶段、日期后应得出相同的共有指标。

### 6.2 补齐不可恢复的时间历史

现有当前时间戳及部分文案入队事件不足以精确重建所有图片处理、负责人切换、后台等待时段。因此新增轻量的追加式 `operator_work_events`，而非依赖 `updated_at` 反推。

建议字段：

- `id`、`task_id`、`stage`、`event_type`、`occurred_at`、`recorded_at`。
- `worker_account_id`（被统计人员）、`actor_account_id`（动作执行人）、发生时身份与角色快照、前后负责人。
- `copy_revision_id`、`image_run_id`、`approval_event_id`、`sampling_item_id`、`rework_chain_id`。
- `from_phase`、`to_phase`、`reason_code`、`release_method`、任务类型/批次/图片页数等最小统计快照。
- `source_kind`、`source_id`、唯一 `event_key`、`data_quality`、`schema_version`；唯一键结合来源事件、事件类型、阶段及必要的任务标识，确保重放幂等。

事件覆盖：分配/改派、阶段进入、可人工处理开始/结束、提交、退回关联、后台开始/结果就绪、首次及后续放行、取消。质检结论仍以原业务事件为准，新增记录只关联原事实；不维护第二套相互矛盾的审核结论。

新事件与业务状态更新在同一事务内写入，服务端获取操作者、使用数据库时间；后台结果就绪也必须记录。所有入口包括工作台、作业模式、批量动作、管理员代作、机器回调都覆盖，避免只记录某个按钮路径。

采用单一事件写入机制：任务行状态/归属迁移由数据库触发器统一捕获，业务专属提交、退回、放行事件由事务中的业务函数显式写入；两者使用不同事件类型与幂等键，不对同一语义重复记账。后台可操作条件由共享分类规则判定，支持“状态名未变但结果已就绪”。

同任务同阶段的时间片分类互斥：未分配、人工待办、机器排队、机器执行、待质检、批次等待。需要并发处理的请求按区间并集与明确优先规则归类；不能重复叠加同一段自然时间。仅部分页面在后台处理、其他页面仍可编辑时，标记混合状态并保留细分依据，不假定整套都不可操作。

已有任务在启用时写入 `BASELINE`，表示从该时点开始可追踪。只有旧事件链确实完整才能回填历史时长；缺少起点、身份或版本链的样本返回缺失，显示时长覆盖率与开始采集日期。

新账本保留最小事实，不存正文、图片、提示词或凭据。需要任务删除后仍可核对的统计快照不得随任务级联删除；任务详情可标记已删除。旧业务事件已经因删除丢失的部分不可恢复，回填报告明确缺失。

### 6.3 聚合、接口及权限

新增中心模块 `server/src/operator-performance.mjs`、共享口径模块 `src/operator-performance.mjs`；`postgres-repository.mjs` 仅接线，不继续堆叠完整报表实现。

建议只读接口：

- `GET /v1/admin/operator-performance`：团队卡片、分页人员表、样本和数据质量说明。
- `GET /v1/admin/operator-performance/:accountId`：单人趋势、质量、耗时、原因分布。
- `GET /v1/admin/operator-performance/:accountId/tasks`：某指标对应的分子、分母或排除明细。
- `GET /v1/admin/operator-performance/export`：与上述筛选一致的导出；注册顺序避免被动态人员路由匹配。

公共参数：`period/from/to`、`accountId`、`stage`、`batchId`、`taskType`、`policyVersion`、`dateBasis`、`metric`、`sampleSet`、`page/pageSize`、`sort/order`；只允许白名单。排序字段映射固定 SQL，查询使用参数绑定，不接受任意 SQL 或前端指定统计身份。

返回包含 `range`、`timezone=Asia/Shanghai`、`asOf`、`metricVersion`、`snapshotToken`、`summary`、`people`、`pagination`、`dataQuality`。率为 `{passed, failed, decided, pending, excluded, rate}`，排除数量带原因；耗时为 `{samples, medianMs, p90Ms, meanMs, missing}`，明确缺数据与零样本的区别。

日期按北京时间首日含、末日含，SQL 使用起点含、次日零时不含。一个汇总请求使用同一只读数据库快照。明细通过受限短期 `snapshotToken` 对齐指标集合：首次查询保存有界的样本 ID 与结果快照或使用具备记录时间水位的事实层；仅传一个时间戳不足以保证回填后的跨请求一致。令牌过期或明细事实已删除时明确提示重新计算，不静默展示另一组数据。

服务端执行 SQL 聚合和分页，不逐个账号调用个人统计接口，也不把全量任务/图片详情拉到浏览器。初期按请求聚合，私有短缓存 30–60 秒、同键请求合并、写入后失效；缓存键包含认证身份、权限版本、全部筛选及指标版本。前端使用现有工作区更新信号和可见页刷新。

新接口只允许实时认证有效的 ADMIN，Next 代理和中心均校验。个人接口保持只能读本人。匿名质检身份不能因普通用户访问统计接口被揭示。失去权限时清除缓存结果并返回 403，而非返回旧报表。

索引围绕“账号/阶段/时间/任务”及“任务/阶段/事件顺序”建立；抽检需支持按任务选最早随机样本、按质检项取首个结论。迁移前检查现有索引，避免重复；用测试数据 `EXPLAIN ANALYZE` 验证实际查询计划。大数据超出限制时明确要求缩小范围，不能静默截断或展示未经标注的部分人员排名。

后续确有性能需要再增加日聚合表，保存计数及可合并的分布数据；不能平均每日中位数/P90 得到全期中位数/P90。此方案不要求新增生产定时任务。

## 8. 实施顺序

1. **指标与事实层**：固定上述口径及 `metricVersion`，构造可手算的测试样本；抽出个人/管理员共享质量事实，排除直放、自检和批次影响混算。
2. **管理员质量与产量**：中心汇总接口、完整人员表、阶段首轮通过率、复检、提交贡献、退回明细、样本提示。此阶段只展示可由现存事件可靠恢复的历史数据。
3. **时间采集与效率**：增量迁移、事务事件、基线与可恢复回填，接入分阶段周转和等待；历史缺失显式标注。采集越早开始，后续覆盖越完整。
4. **详情、对比与导出**：统一筛选、报表快照、原因和趋势、历史下钻，补齐当期已放行/当前有效/已交付的区别。
5. **验收与兼容切换**：只在测试环境执行迁移与假数据全流程；用固定数据核对个人/团队。上线顺序为数据库增量结构 → 中心 → Web。新 Web 遇到旧中心应明确提示该能力未就绪，不退回旧的错误人员通过率。

交付范围包含代码、迁移、测试、指标说明与回填覆盖报告。生产发布另行安排，方案本身不新增发布或生产调度。回滚应用时保留追加事件和新表，关闭新入口即可；不以删除历史数据作为回滚手段。

## 9. 验收标准

所有自动测试使用假模型和隔离测试数据库，不消耗模型额度。

1. 期间提交 10 个任务，首轮抽中 4 个，其中通过 3、退回 1：首轮通过率必须为 75%（3/4），不能是 30%、90% 或 100%；若 10 个都具备抽检资格，覆盖率为 40%。
2. 上述失败任务返修后通过：首轮仍为 75%，首次复检为 100%（1/1），复检样本不加入首轮分母。
3. 全部未抽中或尚未出结论：显示“—”并展示待审/免检数量，不能显示 0% 或 100%。
4. A 提交后改派 B，质检判定 A 原版本失败，B 修复后通过：A 获得原提交及失败，B 获得返修贡献与复检，时间段按归属拆开。
5. A 提交文案、B 提交图片：团队任务为 1，阶段贡献分别归 A/B，最终放行归对应图片提交者；不存在团队简单累加为 2。
6. 旧结论被 `SUPERSEDED`、任务返工或质量失败后废弃：原首轮事实不丢失，当前完成量可变化但历史首次放行量不被抹去。
7. 整批退回 10 条、其中只有 1 条实际单条失败：显示 1 个有效失败样本和批次影响，不能伪造 10 个首轮失败。
8. ADMIN_BYPASS、管理员直放、自检、重复请求、模拟数据、来源不明与历史缺身份各按定义处理；文案原稿 2.5 分不能计为作业员质检通过。
9. 首轮判定先于日期/账号过滤；北京时间跨日、跨月提交/审核、取消、跨阶段返工都能手工对账。
10. 草稿、心跳、同阶段版本变化不重置等待；后台就绪、改派、提交正确开闭时段。机器生成等待不冒充人员周转，缺失起点不使用 0 补齐。
11. 相同时间范围、同一人员和同一阶段，管理员与个人页的共有指标一致。团队率按样本总数加权，期间去重不误加每日去重。
12. 统计卡片点击后，明细分子/分母可重算卡片；分页、导出、快照过期与并发新增记录不会静默改变样本集合。
13. 非管理员访问他人统计、伪造账号、凭据失效、旧缓存越权均返回拒绝；错误状态与零数据可区分。
14. 在代表性批次规模下测试查询计划、响应体与耗时，证明不随任务数产生逐任务 HTTP 请求；统计上限或超时不会返回假完整结果。

建议验证命令：`npm test`、`npm --prefix server test`、`npm run typecheck`、`npm run build`，另运行项目隔离 PostgreSQL 和假接口浏览器测试，覆盖桌面与移动端。耗时性能目标需依据测试数据规模与环境确定，不能在未测量前宣称达标。
