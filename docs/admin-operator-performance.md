# 管理员人员质量与效率

入口仍为 `/workbench-statistics`，页面默认近 7 天。原生成与当前分配看板在“生成与流程概况”中按需加载。

## 已实现

- 团队概况、全量人员分页表、搜索与排序、日期/阶段/账号/批次筛选，以及 URL 筛选恢复。
- 文案和图片各自的一次通过率、标注整体通过率与质检操作通过率均显示实际分子/分母。账号判定项次、一次通过率、整体通过率和打回率按每次结论时间使用同一分母；质检操作通过率单独按质检人员的逐项通过、逐项退回与整批波及退回项次计算。
- 账号数据的“全部”和“标注”视图默认只统计文案，列名为“文案一次通过率”“文案整体通过率”；显式选图片时只统计图片并显示对应图片列名。这两个视图不提供文案与图片合并选项。“质检”视图保留自身的阶段筛选，并明确显示“质检操作通过率”；生成与流程概况仍可按全阶段查看。废弃列明确标为“首检废弃率”，使用单独的首次质检日口径。现存账号（含已停用）即使没有期间记录也显示，零判定显示 `0.00%` 与 `0/0`；各视图均可排序、查看明细。
- 实际提交任务与提交次数、首次/再次最终放行、退回与重复退回、返修提交、批次退回影响、交付确认任务与批次数。
- 当前人工待办与质检/批次等待；文案、图片人工待办周转的中位数/P90、完整样本数/缺失数；提交到结论及返修总周转。
- 人员与团队指标下钻，同一报表快照内按阶段、指标、通过/退回结论分页；提交版本、操作账号、时间线、退回原因及趋势。
- CSV 导出与当前成功报表一致，包含分子分母、时长缺失、覆盖样本、排除数、时区和报表时间；文本按字面量导出以避免公式注入。
- 个人统计的首轮质量使用同一历史事实，排除免审核完成及明确模拟的图片提交。

## 口径

首轮通过率是任务每阶段在完整历史中最早一次随机抽中的实际审核结果，通过数 / 已出有效结论数。先判定首轮，再按北京时间结论日期筛选。待审、未抽中、免检、快捷直放、自检、模拟及缺失身份不进入分母。无样本为 `null`，界面显示“—”。批次退回影响不自动变成逐条审核失败。

账号的**判定项次、一次通过率、整体通过率、打回率**按北京时间每次有效质检结论的实际时间、实际标注账号和所选内容类型统计。每次有效 `PASS` 或 `RETURN` 都为对应账号增加一个判定项次；同一内容同一天多次有效判定也分别计数。一次通过率分子是其中首轮通过项次，整体通过率分子是其中全部通过项次（一次通过和返修后通过），打回率分子是其中退回项次。昨天退回、今天返修通过会进入昨天的退回和今天的通过；同一天先退回再通过，分母为 2、通过和退回各为 1。跨人返修按每次实际标注账号归属，与当天分配任务数不必相同。账号数据默认选文案，文案和图片分别统计，同一任务即使两个阶段都被质检，默认文案视图也只算文案结论；显式选图片时只算图片。

每次整批打回的可识别波及内容各计一个退回项次，文案触发项若已有逐项打回记录不重复计数；同一天之后通过仍另计一个通过项次。历史整批仅保留总数、无法恢复受影响内容及标注账号时，不将总数平均分摊给任何个人；报表分别提示已知的未归属波及项数，以及范围和数量无法恢复的整批打回次数。**首检废弃率**是独立的管理状态指标，仍按首次有效质检日选取内容，再计算最终废弃数 / 首检已判定内容数。无期间结论时一次通过率、整体通过率和打回率按 `0` 导出和排序，界面显示 `0.00%（0/0）`。CSV 导出按所选阶段标明文案或图片，并保留首检废弃率的独立分母；生成与流程概况的全阶段导出保留原合并列名。

**质检操作通过率**是所选日期内质检人员实际作出的逐项 `PASS` 结论数 /（逐项 `PASS` 结论数 + 逐项 `RETURN` 结论数 + 整批打回波及退回项次）。日期按北京时间的实际操作时间筛选，人员按执行该次质检的账号归属；初检通过与返修后的强制复检通过各计一次，同一任务阶段的多次有效判定分别计入。每次有效整批打回按记录的 `affectedCount` 计数；无有效数量时按完整 `affectedTaskIds` 数组计数。文案整批的触发项已有逐项退回结论，批量范围只包含额外波及项；图片整批没有对应逐项结论，批量范围包含全部波及项。历史记录缺少数量和成员 ID 时，若对应批次仍保留打回后的成员状态，则按该批次成员恢复数量；完全无法恢复时计数为 0，并在详情和历史范围提示中说明。历史记录缺少明细 ID 时仍不能逐项下钻。文案和图片合并时先合计各自通过和退回项次，再相除。无判定时比率按 `0` 导出和排序，界面显示 `0.00%（0/0）`。批量操作次数、管理员快捷直放、质检废弃及提交管理员另行单列。自检、模拟的逐项记录及身份不明的记录排除；整批波及项按批次记录的范围计入。

提交按实际文案批准账号、图片初审提交账号记录；当前待办按现负责人。改派、版本失效、原任务删除不改写已保留的历史事实。团队提交按任务取并集，不能把不同人员的阶段贡献简单相加。首次最终放行归图片提交人；交付确认是确认账号的独立操作记录，不回写前序贡献。

覆盖率使用期间首次提交中**已形成普通抽样记录**的集合：抽中 / 已有普通抽样记录。尚未结批或没有普通抽样记录的首次提交单列，不能把它们都当作已知免检或未抽中。首个返修复检指标仅使用父节点为普通随机抽检的可追溯链；没有这种关联的终审返工仍计入全部强制复检，不冒充首个复检样本。

人工待办周转是同次提交周期中本人负责且可人工处理的自然时间，排除其他负责人时段、机器和后台纯等待；存在结果可确认时视为可人工处理。它包括非工作时间，不是实际工时。均值、中位数、P90 在完整样本上计算，不平均每日分位数。阶段/负责人/后台状态变化记录时间线，心跳与普通保存不重置。

## 数据与接口

`0072_operator_performance.sql` 新建最小统计事实和阶段事件表，以及共用的质检视图；`0087_account_quality_records.sql` 保存账号内容质检事件与首次质检归属；`0089_account_quality_batch_returns.sql` 补全整批退回的成员归属。业务写入触发器在原事务中追加事实，来源键保证幂等。它们不随任务或用户级联删除；只保存统计身份、任务 Query、版本引用和分类，不复制生成正文、图片、提示词或凭据。存量可信事件一次性回填，已删除的旧事件不可恢复。

存量任务从基线开始采集完整处理时段，不反推迁移前工时。当前待办可使用已有的阶段起点/结果就绪时间；完整提交周转没有可靠起点时显示缺失。

管理员只读接口：

- `GET /v1/admin/operator-performance`
- `GET /v1/admin/operator-performance/tasks`
- `GET /v1/admin/operator-performance/:accountId`
- `GET /v1/admin/operator-performance/:accountId/tasks`
- `GET /v1/admin/operator-performance/export`

明细和导出需传 `snapshotToken`。中心实时校验认证、角色和凭据版本，Next 代理拒绝非管理员访问 `/v1/admin/*`。参数、排序和页码均有白名单。当前实现用 SQL 读取指定日期、阶段、账号、批次的有界事实，在中心用共享纯函数完成来源去重、聚合和分页；同一内容的不同有效质检结论仍分别计数。浏览器不读取全量事实，也没有逐任务 HTTP 请求。

每类查询上限 50,000 行，合并事件限制 200,000 条，账号名册限制 50,000 个，超限明确失败；SQL 单次最多 15 秒。只读事务使用一致快照，读取现存账号名册与统计事实；已删除且期间没有任何事实的账号无法从现存名册恢复。服务进程保存最长 5 分钟的结果供分页、明细和导出复用，最多 8 份，事实、时间线与人员数量合计有界；过期、被淘汰或进程重启后要求重新刷新，不改用另一批数据冒充原报表。多个中心实例需让同一报表请求落在同一实例；跨实例未找到令牌会明确提示刷新。暂未引入共享缓存、日聚合或生产调度。

## 升级

上线时先备份，在维护窗口通过现有迁移机制按编号应用全部待执行迁移，确保 `0072_operator_performance.sql`、`0087_account_quality_records.sql`、`0089_account_quality_batch_returns.sql` 依次完成，再更新中心与 Web。本次开发只在隔离临时库验证，没有升级运行中的业务数据库或发布生产。

迁移包含存量事实回填和索引创建，执行耗时随已有审核数据增长。先在业务备份上评估耗时，部署后核对个人/管理员同阶段质量及缺失样本数。旧中心不提供新接口时前端提示升级，不显示旧评分算法作为替代。
