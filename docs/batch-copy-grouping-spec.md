# 批量文案批次分组规格

## 目标

一次“开始批量生成”创建一个唯一批次。该次提交中的所有选题，不论内容分类是否相同，都能通过同一批次名称和批次 ID 找回；成功、运行中和失败记录均属于该批次。

批次分组只用于归档、筛选和恢复，不进入文案提示词，也不改变模型调用次数。现有内容分类继续作为文案输入属性，与批次分组相互独立。

## 用户流程

1. 用户在批量生文页填写多个选题和可选的批次名称。
2. 点击开始时，浏览器为本次提交创建一个新的 UUID 批次 ID；名称留空时生成带本地时间的默认名称。
3. 每条文案任务携带同一组 `batchId`、`batchName`，并继续按现有规则顺序执行、单条失败隔离。
4. 页面提供最近批次筛选。选择批次后展示该批次内已完成文案以及运行中、失败任务。
5. 单条生成入口保持兼容，其记录没有批次元数据并显示为未分组。

## 数据与 API 契约

- `batchId`: 标准 UUID；历史或单条记录可为 `null`。
- `batchName`: 去除首尾空白后的非空字符串，最多 100 个 Unicode 字符；历史或单条记录可为 `null`。
- `POST /api/copy-generations` 新增可选对象 `batch: { id, name }`。对象存在时两个字段必须同时有效。
- 服务端任务记录是批次归属的事实来源。任务完成写入文案历史时，从任务继承批次字段，避免客户端提交内容不一致。
- `GET /api/copy-generations` 支持可选 `batchId` 筛选，并返回最近批次摘要。
- 批次摘要至少包含 ID、名称、总数、完成数、失败数、运行中数量和最后活动时间。
- 已完成任务只通过文案历史计数；任务表仅统计未完成/失败任务，避免重复计数。

## 数据库迁移

- 在 `standalone_copy_generations` 和 `standalone_copy_generation_jobs` 上增加可空 `batch_id`、`batch_name`。
- 旧数据库原位增加可空列，不回填、不推断历史批次。
- 不新增独立批次表；批次摘要由现有任务和结果记录聚合得到。

## 安全与边界

- 外部输入不可信；API 和存储层均校验 UUID、名称长度及成对出现规则。
- 批次名称仅作文本展示，React 默认转义；不得拼入 SQL、文件路径或模型提示词。
- 保持准备语句、整数任务输出目录、串行执行和现有费用确认规则。
- 不增加发布、生产调度或额外模型调用。

## 测试与验收

- 存储测试覆盖：任务批次持久化、失败恢复、完成继承、按批次筛选、摘要计数、非法输入和旧库迁移。
- API/UI 契约测试覆盖：同一提交只创建一次批次 ID、每条请求发送同一批次、名称自动生成、最近批次筛选和状态展示。
- 运行定向测试、全量 `npm test`、`npm run typecheck`、`npm run build`、Mock smoke。
- 在可用的已登录浏览器中检查桌面和窄屏交互；若登录环境不可用，明确记录限制。

## 成功标准

- 混合数码、家居、旅行等内容的一次批量提交，在一个批次下完整可查。
- 页面刷新后仍可按批次找回成功和已开始但失败的记录。
- 同名的多次提交仍由不同批次 ID 区分。
- 单条生成、内容分类、人工质检和后续批量生图行为无回归。
