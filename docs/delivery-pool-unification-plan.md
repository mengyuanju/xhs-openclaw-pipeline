# 交付池统一状态与批量归档方案

日期：2026-09-18。状态：主体功能已实现；实际接口、使用步骤和升级说明见 [共享交付实现说明](shared-delivery.md)。下文保留设计依据。

业务口径已确认：作业人员和管理员都可以直接对外交付，共用同一份交付状态。管理员汇总保存作业人员已经交付的内容，不构成再次交付。

## 1. 当前问题与代码依据

本方案依据当前工作区代码；未连接生产数据库，不把代码问题等同于已经核实的线上数据故障。

| 当前实现 | 造成的使用问题 |
| --- | --- |
| `server/src/final-delivery.mjs` 的两端列表都读取 `delivery_entries`、`delivery_batch_items` 和 `delivery_batches` | 数据表已经共用，问题主要在查询范围、状态定义、操作限制和刷新机制 |
| `delivery-pool-workbench.tsx` 中管理员默认 `PENDING`，作业人员默认 `ALL` | 作业人员打包后，内容从管理员默认列表消失，容易误以为没有同步 |
| `delivery-batches.mjs` 的普通用户历史、详情、文件访问均限定“本人创建的作业员批次” | 管理员打包了本人任务，作业人员的交付历史仍看不到这个批次 |
| 列表行把已进入任意批次的内容统一显示为“已打包” | 返回的确认状态、确认时间没有充分展示，无法直接辨别已打包但尚未交付与已确认交付 |
| `deliveryForActor` 隐去其他人的打包人、确认人 | 作业人员无法知道管理员何时替其完成操作 |
| `0054_delivery_batches.sql` 的版本唯一约束和 `createDeliveryBatch` 的查重 | 同一版本只能建立一次原始交付批次，管理员不能把多个已交付批次的部分内容再次汇总成包 |
| 交付池只支持打包状态、词包、甲方批次等部分服务端条件，文本搜索仅过滤已加载内容 | 缺少统一的时间、交付状态、交付人筛选，无法可靠地按完整结果批量操作 |
| 总池历史固定取前 50 批；个人历史有分页和状态筛选，但没有日期筛选 | 历史数量增加后查找困难，两处体验不一致 |
| `workspace-updates.ts` 是同浏览器的失效通知；交付池没有接入，其他设备也收不到 | 切页或人工刷新前可能持续展示旧状态 |
| `personal-workspace.mjs` 按批次创建者统计交付记录 | 管理员代为打包、确认后，个人统计也可能与交付池不一致 |

## 2. 统一业务规则

### 2.1 以任务版本为单位

一份交付内容的唯一身份为 `(task_id, copy_revision_id, image_run_id)`。所有页面都读取服务端对这个版本计算出的状态，不能按“谁创建了批次”计算是否已交付。

| 主状态 | 判定 | 作业人员与管理员共同看到的内容 |
| --- | --- | --- |
| 待打包 | 当前版本通过全部门禁，尚无原始交付批次 | 可交付时间、负责人、未打包 |
| 已打包，待交付 | 当前版本已有原始批次，尚无有效交付确认 | 打包人、打包时间、原批次、下载记录 |
| 已交付 | 当前版本已经由有权限的人明确确认对外交付 | 确认人、确认时间、原批次 |

“未交付”是前两项的合计。“版本更新待重交”是附加标识：当前版本未交付，但该任务的旧版本曾经交付。旧版本仅打过包的，标识为“版本已更新，需重新打包”，不能称为已交付过。

内容返工或门禁撤回时，当前内容不得继续用于新的交付确认；已交付旧版本的历史仍保留。新版本审核通过后拥有独立状态，旧版本的“已交付”不能继承给新版本。

### 2.2 打包、下载、交付、汇总保存分别记录

- 创建原始包：变为“已打包，待交付”。
- 下载：记录谁下载、何时下载，不自动变为“已交付”。服务器传输完成也不能证明文件已保存在本地或已发给接收方。
- 确认交付：操作人明确确认后，改变所选版本的共享交付状态。
- 汇总保存：把已交付版本收集为一个可下载文件，记录归档信息；保持原确认人、确认时间、交付数量不变。
- 管理员先打包，作业人员看到“管理员已打包，待交付”；管理员确认后，双方看到“已交付”。反向操作规则相同。
- 已交付内容再次下载或归档，不产生新的交付次数。第一期按一次有效交付记录管理，不引入多接收方分发流程。

### 2.3 支持逐条和批量确认

确认对象为条目集合。一个 30 条的批次可以先确认 20 条，批次显示“已交付 20 / 30”；剩余 10 条继续处于待交付。只有全部成员确认，批次才显示“全部已交付”。

保留现有“先有下载记录，再确认交付”的操作约束，并改为检查当前操作人对所选内容的下载记录。混合批次中的作业人员可以下载自己的子集，再确认自己的条目；不能因管理员下载过整包，就视为该作业人员也已下载。

两人同时确认同一版本时，先提交的一次生效；后一次返回“已于某时由某人确认”，不覆盖原确认人、不增加交付计数。

## 3. 页面方案

### 3.1 共用一套页面和查询逻辑

管理员使用“总交付池”，作业人员使用“我的交付池”。共用状态标签、日期组件、列表、历史组件及查询契约，由服务端决定可见范围和可执行操作。

页面包含三个视图：

1. **交付内容**：当前通过门禁的版本，可切换全部、未交付、待打包、已打包待交付、已交付；新进入页面默认“全部”。
2. **交付记录**：按条目查看全部历史版本，按批次分组查看也可以；包括管理员操作的本人内容。支持分页，不限前 50 批。
3. **汇总保存记录**：管理员查看已生成的汇总包、范围、数量、归档人、生成时间、下载记录和失败原因。

个人页面保留“与我有关 / 我操作的”切换，默认“与我有关”。同一管理员批次包含多人的内容时，个人只看到与本人有关的条目和数量。

顶部显示“可交付总数、未交付、已交付、版本更新待重交”；未交付卡片细分“待打包 / 已打包待交付”。这些卡片反映当前人员、来源、搜索、日期范围，忽略当前状态标签，便于切换；表格结果数则应用全部筛选。页面明确标注这一统计口径。

列表建议列：

| 内容 | 当前负责人 | 交付状态 | 打包信息 | 交付信息 | 汇总保存 | 操作 |
| --- | --- | --- | --- | --- | --- | --- |
| 任务号、Query、版本 | 账号显示名 | 已打包待交付 / 已交付及更新提示 | 打包人、时间、批次号 | 确认人、时间 | 未归档 / 最近归档时间 | 预览、下载、确认、历史 |

作业人员端可简化来源和负责人列，但不能隐去本人条目的打包人、确认人及时间。跨角色显示业务名称和角色，不返回无关账号资料。

每条详情展示时间线，例如“09:10 通过门禁 → 09:30 管理员王某打包 → 09:35 作业人员李某下载 → 10:00 李某确认交付 → 17:00 管理员汇总保存”。

### 3.2 双方都有的筛选

| 条件 | 选项 / 行为 |
| --- | --- |
| 交付状态 | 全部、未交付、待打包、已打包待交付、已交付 |
| 版本情况 | 全部、版本更新待重交、历史版本；历史版本在交付记录中查找 |
| 日期依据 | 可交付时间、打包时间、交付确认时间、最近状态变更时间；归档记录另有归档时间 |
| 日期范围 | 全部、今天、昨天、近 7 天、近 30 天、自定义开始与结束日期 |
| 文本 | 任务号、Query、交付批次号；服务端查询完整结果 |
| 人员 | 管理员可选当前负责人、交付确认人、打包人；三者分别命名 |
| 来源 | 管理员可选词包、甲方批次；作业人员沿用现有来源信息权限 |
| 汇总保存 | 管理员可选全部、未汇总保存、已汇总保存 |

默认不限制日期，防止旧的待交付内容被隐藏。查看某天未交付内容，使用“可交付时间 + 未交付”；查看某天已交付内容，使用“交付确认时间 + 已交付”。没有确认时间的条目不会匹配确认日期；冲突组合显示说明，不暗中改用任务创建时间。

业务时区固定 `Asia/Shanghai`，数据库存 UTC。日期结束按次日零点排除式边界处理，例如 9 月 18 日表示 `[9/18 00:00, 9/19 00:00)`。筛选状态写入 URL，刷新和返回页面保持一致。

### 3.3 批量操作

- 待打包：`打包并下载所选`。
- 已打包待交付：`下载所选内容`、`确认所选已交付`。
- 已交付：`重新下载所选`；管理员增加 `汇总保存已交付内容`。
- 同时选择多种状态时，各操作明确显示可执行数量；确认前展示完整范围，不能静默跳过后声称全部成功。
- 区分“选择本页”和“选择符合条件的全部 N 条”。继续保留手动选择最多 200 条；全量汇总使用服务端冻结结果和分卷，不能只汇总浏览器加载到的部分。

## 4. 管理员汇总保存流程

典型操作：“交付确认时间 = 今天，状态 = 已交付，归档 = 未汇总保存”，选择所有结果，点击汇总保存。

1. 服务端预检：返回实际条数、任务数、涉及人员/原批次、预计体积，以及不可用项；状态为未交付的条目不能混入这个操作。
2. 管理员在预检结果中确认范围。服务端生成短期有效的选择快照，绑定管理员、筛选条件和确切版本。
3. 创建持久化的汇总任务。冻结成员、原交付时间、原确认人和来源批次；状态为 `QUEUED → RUNNING → SUCCEEDED / FAILED`。
4. 从已冻结的原交付文件提取精确成员，生成汇总 ZIP 和清单，不读取任务的最新版本替换历史内容。图像原字节保留。
5. 生成成功并校验文件后，标记这些条目“已汇总保存”。支持在历史中重复下载原汇总包。

同一条目可出现在多个汇总包中，不改变原始版本唯一性。默认选“未汇总保存”，管理员也能显式重新归档。文件名使用归档编号、日期和条数；归档历史保存查询条件和冻结成员。

推荐包内结构：`清单.xlsx`、`manifest.json`、`任务整数ID/版本目录/文案与图片`。清单含任务号、版本、历史负责人、原始批次、确认人、确认时间、归档编号及文件路径。文件系统落盘沿用受控存储规则，不能由 Query、账号名称或筛选文本拼接真实目录。

历史批次缺少可识别的成员路径时，先按已有 ZIP 格式核验成员映射并建立索引。不能把整批未选内容装入包，也不能拿当前任务内容冒充历史快照。原文件缺失、哈希不符或成员无法定位时返回具体条目，预检阶段阻止提交；生成期间发现异常则任务失败，不生成缺件的“成功包”。

大包按条数和未压缩体积双重限制分卷，首版建议每卷最多 200 条或 1 GiB，单次最多 2,000 条，阈值配置化并经容量测试调整。超过上限要求缩小范围，不静默截断。输出采用流式写入，不能把所有图片同时读进内存。

“保存成功”指服务器已保留可重新下载的完整归档；浏览器下载只是下载记录。两者在页面单独展示。

## 5. 数据与接口方案

### 5.1 保留现有原始批次

继续使用 `delivery_entries` 记录门禁可交付状态，`delivery_batches / delivery_batch_items` 记录原始包及冻结版本。保留 `(task_id, copy_revision_id, image_run_id)` 的原始批次唯一约束。汇总保存不再调用 `createDeliveryBatch`。

新增以下职责明确的数据结构，最终名称可随实现调整：

| 表 / 投影 | 主要字段与约束 |
| --- | --- |
| `delivery_item_confirmations` | 每个 `delivery_batch_item_id` 至多一份当前有效确认；确认人账号 ID、显示名快照、确认时间、并发版本号 |
| `delivery_item_events` | 追加式记录打包/条目下载/确认等事件、操作者、发生时间、入库时间、来源、幂等键；不覆盖历史 |
| `delivery_item_participants` | 条目所属负责人账号 ID 和显示名快照、身份依据；用于历史可见范围和归属，不只保存用户名 |
| `delivery_archive_jobs` | 请求人、筛选快照、幂等键、生成状态、错误、产物位置/哈希/大小、生成完成时间 |
| `delivery_archive_items` | 汇总任务与原始条目的关联，唯一 `(job_id, batch_item_id)`；冻结交付信息及成员文件索引 |
| `delivery_archive_download_events` | 汇总包下载人及时间，与交付确认事件分开 |

统一的交付进度查询将门禁记录、原始批次、条目确认、历史版本和成功归档关联起来。列表、卡片、历史、个人统计和导出选择器复用同一个授权条件和筛选构建器，所有 SQL 使用参数绑定。

现有批次 `status` 作为兼容字段：全体成员确认才为 `DELIVERED`；否则继续反映原有 `GENERATED / DOWNLOADED`。新增 `deliverySummary` 返回可见成员数、已确认数、待确认数，以及 `NONE / PARTIAL / ALL`。新界面根据这个汇总展示部分交付，不用下载枚举推断交付状态。

旧的批次确认接口也调用新的逐条确认服务，在同一事务更新条目确认、事件和兼容批次状态；禁止形成两套写入路径。

### 5.2 查询接口

扩展 `GET /v1/delivery-pool`、`GET /v1/delivery-batches`，增加条目历史接口 `GET /v1/delivery-items/history`。统一支持：

`deliveryState`、`versionState`、`dateField`、`from`、`to`、`search`、`assigneeAccountId`、`deliveredByAccountId`、`packedByAccountId`、`archiveState`、来源及分页参数。

日期、状态和人员 ID 由服务端白名单校验；普通用户传入其他人的 ID 不能扩大范围。条目返回 `deliveryState`、`packedBy/At`、`deliveredBy/At`、`lastArchivedAt`、`isCurrentVersion`、`rowVersion` 和允许的操作。

列表和卡片在同一读取快照中生成，避免并发确认时数量互相矛盾。所有排序增加稳定 ID 作为第二排序键；批量全选通过快照冻结，不能依赖不断变化的分页位置。

### 5.3 写入与文件接口

| 接口 | 用途 |
| --- | --- |
| `POST /v1/delivery-items/confirm` | 明确版本和条目集合，确认全部所选；支持幂等键 |
| `POST /v1/delivery-items/archive` | 下载允许访问的已打包条目子集，不建立新的原始交付批次；支持从管理员混合批次提取本人内容 |
| `POST /v1/delivery-archives/preview` | 管理员预检“已交付内容”的选中集合或全部筛选结果，签发选择快照 |
| `POST /v1/delivery-archives` | 根据选择快照创建汇总任务，返回持久化任务 ID |
| `GET /v1/delivery-archives`、`GET /v1/delivery-archives/:id` | 汇总记录、任务进度、失败原因 |
| `GET /v1/delivery-archives/:id/download` | 下载成功生成的汇总包或对应分卷 |

逐条确认校验操作者权限、确切版本、当前门禁、下载记录和已有确认；全部条件成立才在短事务中写入。未授权、版本变化等失败返回逐项原因，保持本次写入原子性；已确认成员作为幂等成功处理。

汇总预检和创建间状态变化时重新校验；返回需要重新确认的差异，不自行增加、替换或删除成员。任务重试复用原冻结成员，重复请求同一个幂等键返回原任务。

文件生成在事务之外执行。临时文件校验、原子落盘后再提交成功状态；进程退出后能够恢复或将中断任务明确标记失败，不能永久停在运行中。未成功的任务不计入已归档。这里只设计用户主动触发的后台文件生成，不新增发布或生产定时调度。

## 6. 可见范围与同步

- 管理员：查看全部正式内容及记录，打包/确认有资格的条目，汇总全部已交付内容。
- 作业人员当前池：本人当前负责的正式内容，不受原始包创建人角色限制。
- 作业人员历史：本人作为负责人快照、打包人或交付确认人参与的条目；原负责人保留历史记录可见性。改派后修改权限以当前负责人为准，历史可见不意味着仍可确认。
- 作业人员只可下载授权条目。管理员混合批次的整包链接不开放给作业人员；提供本人子集下载。个人的批次明细、数量、筛选项和导出内容均按可见成员裁剪。
- 历史账号归属使用账号 ID；账户删除再新建同名账号，不能继承原账号历史。
- 个人统计明确区分“本人负责内容的交付进度”和“本人执行的交付确认数量”；管理员代为确认计入前者，不冒记为本人执行。

第一期同步机制：操作成功立即重取服务端状态，接入现有同浏览器失效通知；页面重新聚焦时刷新；页面可见时每 15 秒检查一次服务端变化，失败退避至 60 秒，并显示更新时间及失败提示。其他设备在正常网络下的验收目标为 15 秒加接口响应时间内更新。

这不是页面自动确认交付，仅同步显示。暂停隐藏页轮询，回到页面立即刷新。保持筛选和滚动位置，合并新状态；失效的勾选明确提示，提交前再次服务端校验。数据请求禁止共享缓存，前端旧请求结果不得覆盖新请求。

## 7. 历史迁移和上线顺序

1. 先核对实际部署版本、迁移记录和同一任务在两角色下的接口响应，确认线上是否存在额外的版本或权限差异。
2. 新增表和索引；按旧批次回填条目状态：`DELIVERED` 才迁移为已交付，保留原确认人和时间；`GENERATED / DOWNLOADED` 迁移为已打包待交付。
3. 旧批次的全量确认拆为对应成员的确认记录，注明 `LEGACY_BATCH_CONFIRM` 来源，记录迁移入库时间；可重复运行且不重复生成记录。
4. 负责人优先从原始身份记录和 `task_assignment_events` 按打包时点恢复。无法可靠还原的标记历史归属未知，管理员可见，不猜测归到当前同名账号。
5. 保留原批次号、ZIP、哈希和追加式历史，不解除版本唯一约束。迁移对账按已确认版本数、待确认数和批次数核对。
6. 先部署兼容后端，再切换双端页面及个人统计，最后启用汇总保存入口。后端未具备新能力时不显示误导性按钮。
7. 上线前同时备份 PostgreSQL 与交付文件存储。需要回退时关闭新入口、保留新表和事件；开始出现逐条确认后，不能直接退回只认识整批状态的旧写入服务。

## 8. 实施范围与验收

建议作为同一需求分三步交付，每步可单独验证：

| 顺序 | 交付内容 | 主要代码位置 |
| --- | --- | --- |
| 1 | 统一条目状态、历史可见性、状态人数统计、迁移和写入兼容 | `server/src/final-delivery.mjs`、`delivery-batches.mjs`、`personal-workspace.mjs`、仓储与迁移 |
| 2 | 双端状态/日期筛选、逐条/批量确认、本人子集下载、自动刷新、历史分页 | `app/delivery-pool/`、`app/workbench/operator-delivery-history.tsx`、`app/components/workspace-updates.ts`、接口代理权限 |
| 3 | 管理员汇总预检、后台文件生成、清单、分卷、归档历史与重下 | 新增归档服务、`http-server.mjs`、文件存储、归档界面 |

必须通过的验收场景：

1. 管理员打包 A 的任务：A 的内容、历史显示管理员和打包时间，状态仍是待交付。
2. 管理员确认 A 的任务：A 显示同一个交付状态、确认人和时间；个人负责内容统计同步增加。
3. A 打包并确认：管理员的已交付列表和当天筛选出现该内容，未交付数量同步减少。
4. 管理员的批次混合 A/B 共 30 条：A 只看到本人条目，可单独下载确认；B 的数据和文件不外泄；管理员看见部分交付进度。
5. 批次 30 条中确认 20 条：按已交付筛选并汇总只得到这 20 条，包内清单、文件数与页面一致。
6. 管理员汇总 A/B 已交付的 80 条，重下或再次归档后仍是原来的 80 条有效交付，原时间和确认人不变。
7. 两人同时确认、重复点击、网络重试：只有一次有效确认；两管理员同时首次打包，同一版本仅建立一个原始批次。
8. 旧版本交付后返工：旧历史和原 ZIP 可追溯；当前版本门禁通过前不可交付，通过后标记待重交。
9. 上海时间午夜边界、分页和“筛选全部”：不漏当天最后一秒的数据，不只导出已加载的一页。
10. 改派、删账号后同名重建、任务/词包被删除：历史不被错误挪给新账号，管理员可按冻结清单查证。
11. 原文件缺失、生成中断、磁盘失败：显示明确失败，不产生空包，不误标已归档；重试不替换成当前任务版本。
12. 两个账号、两个浏览器会话同时打开：一端操作后另一端在规定刷新窗口内显示相同状态，断网时展示未更新提示。

实施测试使用数据库测试夹具和文件假数据，不调用模型、不消耗模型额度。迁移在独立临时数据库中验证，生产升级需要按实现说明执行。
