# 执行机并发真实测试记录

测试日期：2026-09-05。本次按用户明确要求调用真实模型，使用本机临时 PostgreSQL 和本机新版中心。已连接的远程中心仅提供已发布设置、提示词和知识，没有部署、创建或领取远程业务任务。

## 环境与测试方式

- Node.js 24.19.0、PostgreSQL 18.4、Codex CLI 0.152.1，使用当前 ChatGPT 订阅登录。
- 文本/审核驱动模型 `openai/gpt-5.6-sol`，图片模型 `openai/gpt-image-2`，联网检索 `deepseek-v4-flash`。知识匹配使用复制的 99 条已发布知识。
- 任务池文案 3、图片 2；共享 Codex 调用上限总计 5、图片 2。测试命令临时覆盖这些容量，没有更改本机 `.env` 或远程生产配置。
- 三条普通生活类需求：租房书桌收纳、通勤包清单、公园野餐准备。文案阶段结束后，在本机审核成功文案的前两条，各生成 3 张图片。
- 使用真实任务领取、执行记录、图片校验及上传链路。自动化回归中的 fake 与本次真实结果分别保存。

复测任务峰值达到 **文案 3、图片 2**；模型调用实测总峰值为 **3**，原生生图/改图峰值为 **2**。配置总上限为 5 并不代表本批每时刻都有 5 个模型调用。

## 真实结果

| 运行 | 文案结果 | 图片结果 | 主要发现 |
| --- | --- | --- | --- |
| 首轮 `parallel-live` | 2/3 成功，成功项 213 秒、266 秒 | 0/2 任务成功 | 网络重连提示导致文案失败；新生图误用编辑指令；exec JSONL 缺少原生图片事件 |
| 图片协议修复后 `parallel-fixed` | 2/3 成功，成功项 161 秒、211 秒 | 2/2 任务成功，6/6 图片通过模型校验并上传 | 一条文案的 DeepSeek 搜索 JSON 无效；图片主要耗时来自生成和局部修复 |
| 搜索 Schema 后 `copy-search-fixed` | 单条在搜索阶段失败，约 111 秒 | 本轮未生图 | JSON 本身完整，但前置说明＋代码块触发旧解析器拒收 |
| 最终 `copy-final` | 原失败文案成功，178 秒 | 本轮未生图 | 检索一次通过；正文发生 1 次长度调整 |

最终单条文案复验：审核 12 秒、99 条知识匹配 71 秒、真实检索 40 秒、正文生成 37 秒及长度调整 18 秒。搜索没有重复调用。三个测试选题均已有成功文案；这来自分次真实复验，不能把第二轮 2/3 成功改写为同批 3/3。

第二轮图片任务分别耗时 **571 秒（9 分 31 秒）**和 **663 秒（11 分 3 秒）**，两任务并行图片阶段约 **11 分 3 秒**。从第一条文案领取到最后一套图上传约 **14 分 35 秒**；含临时环境准备约 **14 分 43 秒**。

6 张最终 PNG 的生成尝试数分别为 `2/1/1`、`3/1/1`：共 9 次原生图片调用，包含 3 次局部质量修复。后续页首次生成会携带风格参考，记录为 IMAGE_EDIT，不能把全部 IMAGE_EDIT 调用都计成重试。没有中心重复领取或整条图片任务自动重跑。

| 阶段 | 第二轮观测耗时 | 判断 |
| --- | --- | --- |
| Query 审核 | 每条约 14 秒 | 同时执行，没有明显本机排队 |
| 99 条知识匹配 | 每条 69–131 秒，均一次完成 | 主要文案耗时之一；慢调用没有重试，不能归因于执行池卡死 |
| 成功文案正文生成 | 38–43 秒 | 本轮无格式修复调用 |
| 图片规划 | 每套 44–54 秒 | 两套独立执行 |
| 原生生图/改图 | 每次 89–118 秒，不含许可等待 | 图片耗时主体 |
| 单页图文/OCR 校验 | 每次 18–27 秒 | 真实审核调用，质量问题触发局部改图 |
| 整套质量检查 | 每套 35–45 秒 | 通过后再上传 |
| 本机图片上传与完成回报 | 每套低于 1 秒 | 本机测试数据，不代表远程上传耗时 |

多数 Codex 调用的许可等待约 10–25 毫秒；两次后续图片调用等待约 **88 秒**，当时两个图片许可均被占用，属于配置上限下的正常排队。任务内部可以同时准备后续页，但不能突破全机图片上限 2。

## 已定位并修复的问题

1. **新建图被当成编辑。** Codex 提示词原来无条件要求“附件 1 是编辑目标”，首轮无附件时直接报缺少目标。现在 IMAGE 明确从文本新建，IMAGE_EDIT 才要求编辑目标。
2. **已生图却被误判无结果。** 指令修复后，真实 `exec --json` 调用生成了 PNG，但只返回文字和回合结束事件，缺少图片工具项。改为同一 CLI 的 `app-server --stdio`，使用原生 `imageGeneration.savedPath`，仍校验目录、新鲜度、PNG 和业务质量。单图复验 76 秒成功，随后 6 张最终图片完整交付。协议依据[官方 app-server 文档](https://github.com/openai/codex/tree/main/codex-rs/app-server)及本机 CLI 生成的版本化 schema。
3. **已恢复的重连可能被误判失败。** 只有明确重连通知后出现新回答及成功回合时才接受结果；终态错误、额度错误、旧回答和未完成输出仍失败。首轮没有留下完整失败 stdout，不能断言那次已经恢复；相同文本调用单独复跑约 72 秒成功。后续失败保留有界诊断，成功记录重连次数；app-server 握手配置和凭据不进入诊断。
4. **DeepSeek 搜索 JSON 兼容问题。** 未转义引号在独立真实搜索中再次复现，耗时约 37 秒。改用 `text.format.json_schema` 约束摘要和来源字段，保留完整、脱敏的搜索响应及语义失败。独立真实搜索约 62 秒成功，返回 5 个来源；随后完整文案复测发现另一种输出：说明文字后跟完整 JSON 代码块。补充单个终端 JSON 代码块提取，拒绝多对象、多代码块、截断和字符串内的非法引号；保存的真实失败响应经新解析器一次成功接收，额外模型调用为 0。没有增加搜索自动重试，Schema 也不被当作供应商绝不输出畸形结果的保证。接口依据 [DeepSeek Responses API 文档](https://api-docs.deepseek.com/api/create-response/)。
5. **图片质量修复耗时。** 书桌首图的道具小字导致 1 次编辑；野餐首图风格不符，编辑后又缺少“AI生成”标识，合计 2 次编辑。补充提示词优先级：当前页画风优先于旧视觉描述，合规标识不受“无水印”要求影响，道具避免微小文字。没有降低 OCR、内容或质量门槛。

## 结果边界

这是小批量真实测试，不是长期稳定性或订阅并发上限证明。没有用完全相同内容额外跑一组串行基线，因此不声称精确加速倍数。知识匹配及模型响应仍有波动，图片质量修复仍可能发生。最后补充的提示词澄清没有再次生成整套图片，尚不能量化它降低修复率的效果。

现有中心尚未部署并发代码；新执行机需要中心包含 `0007`/`0008` 迁移和 `executorConcurrency` 能力。默认任务并发仍为 1/1，Codex 默认许可仍为总计 2、图片 1；本次 3/2、5/2 属于测试覆盖配置。参见[执行机并发配置](executor-concurrency.md)。
