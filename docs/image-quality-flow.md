# 图片初审与质检流程

## 角色边界

- 普通作业员：查看并修改自己负责的图片，支持重新生图、格式转换、整图编辑、局部编辑、实体替换和历史版本恢复；完成后提交“图片初审”，无法使用时可填写原因废弃任务。
- 图片质检员：必须是启用“图片质检”权限的审核员，只能在独立图片质检池处理分配给自己的项目，不能处理自己提交的图片。
- 管理员：可管理图片抽检配置和审核员权限，也可处理任意图片质检项；不受禁止自检限制。
- 交付池：只允许管理员访问、预览和下载。

## 正常流程

1. 图片生成完成后进入 `MANUAL_ARCHIVE`，由任务作业员逐页初审和修改。
2. 作业员提交初审时，系统固定当前文案版本、图片运行版本和整套图片哈希。
3. 未开启图片抽检或比例为 0 时，当前版本直接放行到 `REVIEWED`，并创建 `READY` 交付条目。
4. 开启图片抽检时，任务进入 `IMAGE_QC_PENDING`。系统按“生产批次 + 图片提交账号”独立累计整数余数，满块立即冻结；不足块等待 30 分钟后至少抽 1 条。
5. 同一冻结批次中未抽中的任务继续等待。全部抽中项通过后，同批任务一起放行到交付池。

## 图片审核备注与后续手工修改

- 图片初审、图片返修详情与作业模式在图片操作面板顶部固定展示“图片审核备注（选填）”，最多 1000 字；尚无备注或图片资产时也保留备注框。任务负责人可填写，其他可查看任务的人员只读查看。说明固定展示：“如需手动修改图片请备注具体点位，图片质检可先通过，后续自行修改后小豆芽替换”。建议写清页码、位置和目标改法。
- 图片返修可以直接提交当前图集，无需在系统内修改或采用新图，备注选填；需要后续手工修改时可写清具体点位，随本轮复检提交保存。未提交草稿在关闭、刷新或切换作业前会提示。
- 备注随图片初审提交保存，绑定当次文案版本、图片运行和图集哈希；提交失败保留输入，并复用同一会话重试。关闭、刷新或切换作业时会提示尚未提交的备注。
- 图片质检列表展示备注摘要并支持展开；普通质检详情和作业模式质检默认显示全文。盲评也保留备注文字，任务、账号等来源信息沿用匿名规则。
- 当前版本的最新提交备注在任务详情和交付预览中只读展示，作为后续手工修改的交接信息，不写入发布标题、正文或图片内容。同一图集可多轮提交，每轮保留独立初审记录和备注，质检项绑定本轮记录；最新一轮的空备注不会回退显示旧备注。新图版本不自动继承旧备注；采用新图时保留旧版尚未提交的文字，作业员核对后明确沿用或放弃，再继续初审。
- 质检员仍手动决定是否通过，备注不改变评分、抽检比例、返工强制复检或待编辑门禁。系统内已有图片编辑请求必须处理完成后再初审或通过质检。
- “小豆芽替换”按系统外手工交接理解；本系统采用新图时仍会撤回旧交付、回到图片初审并重新走抽检流程。
- 升级先应用 `0096_image_manual_modification_notes.sql`，再同步更新中心与 Web；新版 Web 检查任务详情是否支持初审记录，旧中心不能保存非空备注时会提示升级。

## 打回与返修

- 单条打回可以选择仅文案、仅图片或文案和图片；图片返工必须指定问题图片，文案返工必须指定字段，且必须填写明确修改要求。
- 管理员开启“图片质检中显示扣分原因”时，至少要配置一项图片原因，否则前端禁止保存，服务端也拒绝保存。
- 对历史异常配置采用防卡死处理：开关开启但确实没有任何原因选项时，不要求用户选择不存在的选项，仍必须填写修改要求。
- 任何图片质检打回都会设置 `mandatory_image_qc`。任务负责人可在返修详情或图片作业中直接提交当前图集，系统不要求先修改图片或采用新版本，备注也不必填。每次重新提交创建独立初审记录和 `MANDATORY_RECHECK`，固定 100% 复检，不受普通抽检开关和比例影响；同一请求重试不会重复建轮次，再次打回后可继续提交同一图集。
- 返修提交仍校验任务负责人、暂停状态、当前文案与图集完整性，以及待处理图片修改。系统内已有修改请求须先采用、拒绝或取消；这些操作不强制要求改变正式图片。原质检打回记录和旧轮次的备注保留，新一轮由质检员手动决定是否通过。
- 整批打回后，每个成员都要分别返修并强制复检；一个成员通过不会提前释放尚未返修的同批成员。

## 图片环节废弃

- 作业员在自己的图片初审、图片返修详情中使用“废弃任务”；审核员在分配给自己的待质检项中使用相同按钮。普通页面和作业模式均支持。
- 确认时必须填写 1–1000 字的原因，空白内容无法提交；失败重试保留原因并复用请求编号，防止重复记录。
- 废弃整条任务后状态为 `CANCELLED`，保留文案、图片和废弃记录。作业员可以在任务详情查看原因、操作人和时间；审核员直接废弃的项目可在图片质检“已废弃”页查看。
- 服务端检查账号、归属、阶段及版本；运行中的任务或仍有待处理图片修改时，须先完成或取消操作。图片质检仍遵循独立审核和盲评规则。
- 同批尚未完成质检或返修的任务继续等待；其余任务在全部检查完成后放行。废弃项不会被后续整批返修恢复，原有通过或打回结论保留。
- 启用此功能需要执行 `0074_image_task_discard.sql` 并更新中心与网页；中心应提供 `imageDiscardVersion: 1` 能力。

## 盲评与版本门禁

- 盲评审核员可看到匿名编号、质检图片和图片审核备注，不返回任务号、词包、提交人等来源信息。
- 盲评图片使用质检项专用地址，只允许该项目的受派审核员或管理员读取；通用任务详情对盲评审核员不可见。
- 图片版本、文案版本或图片文件哈希发生变化后，已有放行自动失效。
- 交付条目只能由与当前文案、当前图片完全匹配的图片放行事件创建；迁移前已经完成的历史任务使用一次性兼容标记。

## 上线检查

1. 先备份数据库并执行 `0055_image_quality_flow.sql`。
2. 在用户管理中为至少一名审核员开启图片质检权限。
3. 在生产配置中设置图片抽检开关、比例、盲评和审核员整批打回权限。
4. 如开启图片返工原因展示，先确认图片原因列表非空。
5. 检查 `IMAGE_QC_PENDING` 是否存在长期无分配项目；无可用图片质检员时应先补充人员权限。
6. 在开发环境走一次“初审—抽中—通过”、“初审—打回—直接提交原图—强制复检—再次打回—原图复检—交付”及采用新图后的复检链路，再安排正式环境升级。
7. 原图返修复检需要应用 `0097_image_rework_same_version_resubmission.sql` 和 `0098_image_rework_quality_facts.sql`，再更新并重启中心与 Web；迁移保留历史初审、备注及统计事实，解除每个图集只能提交一次的约束，并按具体提交轮次归属统计。

## 开发验证

- 默认测试和类型检查不调用模型，不消耗模型额度。
- PostgreSQL 端到端测试会创建并删除独立临时数据库，不修改当前业务库。
- 浏览器测试使用本地模拟接口验证图片质检页和图片编辑器，不连接正式服务。
- 设置 `RUN_IMAGE_REVIEW_NOTES_BROWSER=1` 运行 `tests/image-review-notes-browser.test.mjs`，覆盖备注填写、失败重试、返修原图直接提交、旧中心保护、版本变化时保留未提交文字及交付回显；使用本地模拟接口，不调用模型。
- 设置 `RUN_POSTGRES_E2E=1` 可直接运行 `server/tests/image-quality-flow-postgres.test.mjs`；测试自行启动并清理一次性 PostgreSQL 18 集群，不读取生产数据库地址。
- 设置 `RUN_LIVE_WORKFLOW_PAID_E2E=1` 可运行 `server/tests/live-workflow-paid.manual.test.mjs`。该测试会真实调用图片和视觉模型，必须保留显式开关；2026-09-15 的验收记录为 3 次 `openai/gpt-image-2` 图片编辑、7 次视觉校验、0 次发布。
