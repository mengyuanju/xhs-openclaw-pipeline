# 隐藏业务规则人工管理：修改细则

日期：2026-09-07。本文保留实施前的规则盘点与修改设计；现已按授权完成代码与验证，生产配置未发布。实际结果和兼容边界见 [实施与验收](./prompt-governance-acceptance.md)。本文补充 [总体方案](./prompt-governance-plan.md)。

目标是让“人工发布的规则 → 模型实际收到的规则 → 程序最终采用的结论”可以逐项对应。每个阶段仅接收自身需要的规则，不把全部模板合成一个巨大提示词。

**1. 三类内容分别处理**

| 内容 | 如何管理 | 示例及边界 |
| --- | --- | --- |
| 业务自然语言指令 | 独立提示词类型，人工编辑、草稿、发布、版本冻结 | 文风、审核尺度、修复方法、评分依据、来源偏好 |
| 程序执行的业务参数 | 明确的配置项，程序和提示词从同一份冻结值读取 | 案例入选分数、修复目标字数、OCR 比对方式；已有质量修复开关/触发分/目标分/次数继续复用 production 设置 |
| 结构契约与当前固定策略 | 展示准确值、来源、版本及影响，不承诺自然语言可改变 | JSON 字段、ID 一一对应、工具协议；当前 400～600 正文范围、评分聚合算法单独注明是现有固定业务策略 |

正文 400～600 范围及评分聚合算法不是模型固有能力限制。为控制本轮改动，它们先沿用并公开；如果需要自由修改整个范围或计算算法，应明确扩大契约/评分引擎范围。不能把固定业务策略伪装成不可改变的技术限制，也不能宣称本轮已支持任意业务算法编辑。

新增简单业务参数拟使用中心已有 global_settings 的 prompt_runtime，并随执行快照冻结。与已有 production 参数不重复存储。提示词中的对应数字由变量生成，避免页面改为 80、代码仍按 70 判断。

**2. 文案审核：清除人称规则的双重覆盖**

现状见 [content-stage-review.mjs:205](C:/Users/HMCD-0005/Desktop/xhs/src/content-stage-review.mjs:205)：

- buildTextReviewPrompt 虽接收管理员编辑要求，随后又追加“第一人称不是必须、最多 WARNING”的覆盖指令。
- [applyTextReviewPolicy:258](C:/Users/HMCD-0005/Desktop/xhs/src/content-stage-review.mjs:258) 再按问题代码和描述识别人称问题，把 BLOCKING 改为 WARNING；若无其他阻断项，还会把 REJECT 改为 PASS。
- 因此，即使模型遵守人工规则拒绝了文案，应用仍可能给出通过结果。

修改方式：

1. buildQueryReviewPrompt、buildTextReviewPrompt 接收冻结的 QUERY_REVIEW_SYSTEM、TEXT_REVIEW_SYSTEM；文案审核同时引用生成该稿时的 TEXT_SYSTEM 编辑要求。
2. 删除固定的人称例外和无条件 applyTextReviewPolicy 降级。第一人称是否必须，由人工发布规则决定；虚构亲测经历仍独立判断，不能混同叙述人称。
3. 保留 JSON 校验和 decision/issues 一致性检查。模型给出 PASS 却包含 BLOCKING 时，走格式纠错或明确失败，不静默改为通过。
4. 若将来确需“某类风格问题仅提醒”，必须是一项明确选择的审核政策；记录原始问题、所用规则和处理后结论。本期不建立任意代码正则降级表。
5. 兼容客户端没有 runReview 时，现有代码会返回带 COMPATIBILITY 来源的 PASS。新运行必须显示“未执行模型审核”；要求独立审核的流程应在调用前报出能力缺失，不能在 UI 上冒充模型通过。历史记录仍保留真实来源。

验收例子：发布“必须以第一人称叙述”，注入模型输出的人称 BLOCKING，最终不得再自动变 PASS；发布允许客观说明后，实际审核请求应使用新规则。不得为了遵循第一人称要求编造个人经历。

**3. 文案修复：保留原编辑要求，只改授权字段**

现状见 [copy-generation.mjs:101](C:/Users/HMCD-0005/Desktop/xhs/src/copy-generation.mjs:101)：

- 长度修复硬写 400～450 个字符，并要求总—分—总。
- 其他格式修复又硬写目标 480～540、标题不得疑问、首段结论前置、末段收束。
- 质检修订另有“必须产生实质变化”的追加规则。
- 这些要求可能与管理员设置的写作结构不一致。仅给初稿读取 TEXT_SYSTEM 无法解决。

细化原方案的 COPY_REPAIR_SYSTEM 为三个独立可编辑条目：

| 类型 | 任务 | 默认修改权限 |
| --- | --- | --- |
| COPY_LENGTH_REPAIR_SYSTEM | 调整正文长度 | 仅 body |
| COPY_REPAIR_SYSTEM | 修复结构/字段校验失败 | 校验错误指向的字段 |
| COPY_REVISION_SYSTEM | 修复质检阻断问题 | 已确认需要修改的字段及有理由的必要联动 |

每种调用都引用本次冻结的 TEXT_SYSTEM 与必要的 COPY_IMAGE_PLAN_SYSTEM，不另设默认文风。模板只说明怎样完成本阶段修复；输入包含上一稿、实际字符数、错误代码、目标范围、允许修改字段。

长度目标由同一配置生成，先限制在现有 400～600 的有效范围内。400～450 和 480～540 的两个隐式目标不再并存。计数继续由程序计算；后续实施应减少依赖错误字符串中写死的数字来分支。

建议长度修复模板的核心句：

> 沿用本次已发布的写作风格与结构，仅修订 body，使其达到传入的长度目标；不得自行增加总分总、第一人称或结论前置要求。保留已有事实与关键步骤，不新增事实，不修改本次未授权的字段。

修复后比较字段差异并重新校验，不能只靠一句“请保留”。body 变化还需复核原配图事实是否成立；有冲突明确进入文案/配图修订，不让生图阶段补写新文案。已进入生图的文字契约保持冻结，修订需形成新的执行输入。

如果模型没有改到阻断问题，记录“修复未解决”并按既有有界重试处理，不以“必须改变任意一项”逼它改坏正确内容。

**4. 图片生成与修复：保留已发布正文，移除强制换构图**

更正此前描述：“正则改写”不准确。当前 [standalone-image-generation.mjs:685](C:/Users/HMCD-0005/Desktop/xhs/src/standalone-image-generation.mjs:685) 与 [pipeline.mjs:72](C:/Users/HMCD-0005/Desktop/xhs/src/pipeline.mjs:72) 是查找特定标记，截掉标记及其后的内容，再追加固定 one-pass 规则。它仍然会改变人工发布内容，甚至删掉标记后用户新增的要求。

修改方式：

- 运行时不再通过标记截断或替换已发布模板。变量填充前保存版本原文，填充后的规则完整进入组合器。
- 场景和文字由模型一次完成的执行方式，放在可见的流程能力说明；可变的字体、留白、背景、卡片偏好进入 IMAGE_SYSTEM。
- 旧版“只画底图、另行叠字”与现流程不兼容时，展示迁移差异和待发布草稿，不偷偷改已发布版本。
- 预检能确定的字段、变量、长度、模式冲突直接报错；自由文本的所有语义冲突无法保证自动识别，页面提供规则并排预览和人工检查。

[quality-repair.mjs:27](C:/Users/HMCD-0005/Desktop/xhs/src/quality-repair.mjs:27) 还有按第 1～5 页固定分配“封面总览/细节解释/行动清单/比较判断/结论收束”的策略。[appendQualityRepairPrompt:178](C:/Users/HMCD-0005/Desktop/xhs/src/quality-repair.mjs:178) 同时要求必须替换完整场景和信息组织，并用 basePrompt.slice(0, budget) 截短原提示词。

准备改成：

1. 由真实的页职责、审核错误和人工 IMAGE_REPAIR_SYSTEM 决定修复内容；不再仅凭页码赋予新职责。
2. 错字问题默认只修文字清晰度；布局问题才允许调整布局；整套重构需要符合已选的修复策略与触发条件。
3. 不管修复范围多大，原事实、逐页文字和页归属不变。若视觉方案本身错误，明确回到规划修订。
4. 修复模板中的策略是可信业务指令；模型审核意见、上一稿等作为待处理数据，不把模型自由文本直接提升成新的规则。
5. 取消静默截短规则。输入超过当前容量时，调用前指明哪个部分超限；保留原文，不能发半份提示词却显示完整版本。
6. 视觉知识配方继续使用其已有版本，在追踪中显示具体追加内容。其现有组合器的长度限制是报错，并非全部都在静默截断；应准确区分。

验收例子：第三页本来是对比页，只因一个错字修复时，不得自动变成“行动清单”，也不能删除已发布提示词尾部规则。

**5. 图片审核：分开记录模型识别与程序比对**

[image-alignment.mjs:271](C:/Users/HMCD-0005/Desktop/xhs/src/image-alignment.mjs:271) 的审核提示词进入 IMAGE_ALIGNMENT_SYSTEM。人工可以调整语义、可读性、版式等验收依据，提示词始终引用冻结的原上图文字。

程序仍负责可确定的比较。当前 [normalizeOcrText:84](C:/Users/HMCD-0005/Desktop/xhs/src/image-alignment.mjs:84) 会 NFKC 归一化并删除空白与引号，置信度阈值固定 0.9；这些不能继续只藏在代码里。

细化建议：

- 页面明确展示文字比较方式。新模式建议只忽略排版换行，引号和标点按实际要求比较；旧的宽松模式仅对历史快照兼容，模式切换必须显式记录。
- OCR 置信度等简单门槛可配置并冻结；它是模型自报值，不作为图片文字真实正确的充分证据。
- 保留“原始抄录 / 程序归一化及差异 / 最终结论”三份证据。程序若依据机械比对纠正模型自报 PASS，必须显示原因。
- 截字、漏字、额外文字无法被“语义相同”放行；看不清应记录不确定，不能补全。
- 允许修改审核提示词不等于允许审核模型改掉锁定文字或关闭本任务约定的文字一致性检查。

程序比较只能验证模型抄录与原文的关系，仍可能遇到 OCR 模型误读。真实验收要查看图像本身，尤其检查裁切区域。后处理裁字缺陷仍按总体方案另行修复。

**6. 质量评分：评分依据可编辑，计算过程可解释**

当前 [quality-scoring.mjs:215](C:/Users/HMCD-0005/Desktop/xhs/src/quality-scoring.mjs:215) 并非简单照用模型总分：它会做维度调整、证据不足时的分数上限、红线/主要问题处理、分层最低分聚合等。

- DELIVERY_REVIEW_SYSTEM 管理各维度怎样评分、何种证据对应好坏。
- 保留现有维度与 0～3 输出契约，先不改整个评分算法；界面显示算法版本 production-v2 及每一步为什么影响总分。
- 原始维度分、程序调整后的分数、最后分数、是否触发修复分别展示，不能覆盖后只留下一个数字。
- 质量修复开关、触发分、目标分和最大次数已存在于 production 设置，直接关联展示和使用，不新造第二套配置。
- “首次分数触发、后续分数需改善”等分支也展示为实际执行条件，避免用户误认为修改评分措辞等于修改重试策略。

这一部分交付的是“评分依据可编辑、现有算法完全可查”；若要人工重新定义维度、权重或聚合方式，需要另列评分引擎改造，不能声称已由提示词实现。

**8. 后台怎样呈现**

每个阶段一个可选择的条目，展示：

- 业务提示词正文、草稿/已发布版本和变量说明。
- 继承哪些上游规则，以及本阶段允许修改哪些字段。
- 关联的执行参数与当前固定契约，链接至唯一配置来源。
- 本次最终请求预览：按业务模板、技术契约、任务数据、参考资料、修复数据分块。
- 真实运行记录：模型原始输出、程序执行的校验/转换、最终结果。

例子：打开“长度修复”，能看到它引用 TEXT_SYSTEM v12、COPY_LENGTH_REPAIR_SYSTEM v2，目标 450～500，现有校验范围 400～600，仅可修改 body；不会出现另一个不可编辑的“总分总”段落。版本和数字只是界面示例，不代表已发布配置。

模板原文 hash、渲染后内容 hash 与最终请求 hash 分开记录，避免变量填充后误认为原文被改写。追踪与发送使用同一构建结果，不能分别拼接。脱敏或截断必须明确标记。

**9. 代码组织与存储边界**

沿用总体方案拟新增的 prompt-catalog、prompt-runtime、prompt-composer、admin/prompt-runtime-service；执行机 agent 只负责传入已有快照。语义修复权限由对应业务模块执行，不塞入中心调度器。

对本次细化需补充：

- 目录增加 COPY_LENGTH_REPAIR_SYSTEM、COPY_REVISION_SYSTEM。
- 可将 OCR 比较方式、案例阈值、长度修复目标等简单参数集中到拟新增 src/prompt-policy.mjs，负责解析与校验，不做任意脚本执行。
- quality-scoring.mjs 增加可解释的计算轨迹/策略描述，初期保留计算结果语义。
- 所有模型调用只取任务开始执行时冻结的配置。既有任务不自动迁移到最新政策。
- 新模板先作为候选草稿导入，旧人工版本完整保留，不自动覆盖或发布。

中心主链路继续复用通用 prompts/settings/snapshot API。现有已配置的参数只关联，不换存储；新增小参数走 prompt_runtime。共享业务模块仍须在执行机部署，不能承诺仅修改页面即可生效。

**10. 验收与拆分方式**

先用 fake client 验证实际构建的请求和程序分支，不消耗模型额度。关键验收：

| 测试 | 必须看到的结果 |
| --- | --- |
| 修改人工文风后触发长度、格式、质检三种修复 | 每次均引用相同冻结编辑规则，无隐藏总分总/人称要求 |
| 模型返回人称 BLOCKING | 程序不再无条件改为 WARNING/PASS |
| 模型能力缺少审核 | 明确未执行或能力不满足，不能显示为真实审核通过 |
| 图片模板含旧标记及其后新增规则 | 不再静默截断；冲突显式呈现 |
| 第三页仅修错字 | 不强制改为行动清单；文字契约 hash 不变 |
| 修复信息超过输入限制 | 调用前报错；不发送截短的人工模板 |
| OCR 返回与原文不一致但自报 PASS | 程序保留识别内容，明确失败原因，不按自报 PASS 放行 |
| 修改案例阈值 | prompt、选择、引用校验、记录全部按同一新值 |
| 调整评分依据 | 模型依据变更可查；固定算法的调整路径不丢失 |
| 发布新版后恢复旧执行 | 继续用历史快照，不偷换规则 |

建议按 3～5 个文件的小任务落地：先统一目录/读取，再分别处理审核、三类文案修复、图片拼接、图片修复、OCR、评分追踪、案例匹配、检索、两类知识分析，最后接入界面并做整链路检查。每项明确实现文件与对应现有 tests 测试文件；避免以一次大提交混合所有行为变化。

实施后分模块运行对应 node:test，最后按实际变更执行 npm test、npm run typecheck、npm run build、必要的中心兼容测试和浏览器验证。真实小样本比较时同时留存模板版本、实际请求、原图、OCR 和程序决策，区分“程序确实用到了人工规则”和“模型是否遵守”，不以提示词已发送推断最终图片必然正确。
