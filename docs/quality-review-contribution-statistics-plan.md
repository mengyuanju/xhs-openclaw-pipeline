# 个人与管理员统计：补齐质检贡献

状态：优化方案，尚未修改业务实现或执行数据库迁移。

## 1. 已确认的问题

当前仓库存在三个相关入口，需分别处理：

| 入口 | 当前口径 | 遗漏原因 |
| --- | --- | --- |
| 个人数据统计 | 初审提交记完成；内容通过率归提交人 | `server/src/personal-workspace.mjs` 的 `PERSONAL_EVENTS_SQL` 只把文案批准、图片初审提交生成为 COMPLETE；没有质检人工作事件 |
| 管理员人员质量与效率（主看板） | 读取历史贡献事实，以事件 account_id 构建人员集合 | `0072_operator_performance.sql` 中 QUALITY 的 account_id 是内容提交人，质检人保存在 data.reviewerId；`src/operator-performance.mjs` 未按 reviewerId 生成质检贡献 |
| 管理员生成与流程概况（折叠面板） | 按当前任务负责人统计 | `src/web-statistics/summary.mjs` 的 resolveWorkOwner 无法表示质检人员的历史工作 |

个人当前待办同样从任务创建人、负责人关系取数，没有按抽检项的 assigned_review_account_id 汇总质检待办。目前“待质检”表示本人内容在等待别人质检，不能直接当成“需要我质检”。

已用共享聚合函数和虚构数据复现：制作人账号 11 的内容由账号 22 质检通过，只会生成账号 11 的管理员人员行，账号 22 不出现。该验证不访问业务数据库，不调用模型。尚未核对线上数据库的具体漏计数量。

## 2. 统一统计原则

分别记录三种关系：当前谁负责制作、哪个账号实际提交、哪个账号实际质检。历史贡献归实际操作账号，当前待办归当前指派账号。账号使用不可变 ID，禁止只用用户名关联。

一条作业可以同时形成制作人和质检人的贡献，团队作业量仍按 task_id 去重。任何账号只要有质检记录或质检待办，就应进入对应人员范围，不要求创建过任务或做过初审；管理员本人实际质检也按相同规则计入。

### 建议指标

| 指标 | 计算方法 | 单位 |
| --- | --- | --- |
| 参与处理作业 | 本人初审提交与逐项质检结论对应的 task_id 并集 | 项作业 |
| 制作提交作业 | 延续现有文案、图片提交口径 | 项作业 / 次提交 |
| 质检完成作业 | 本人已提交有效逐项质检结论的 task_id 去重，文案、图片另列 | 项作业 |
| 质检结论次数 | 按阶段 + 抽检项（含复检轮次）去重；同轮重试不新增 | 次 |
| 质检通过 / 退回 | 本人逐项结论分类，二者相加等于质检结论次数 | 次 |
| 其中复检 | sample_kind 为 MANDATORY_RECHECK 的已完成逐项质检 | 次，属于结论次数的子集 |
| 批量退回 | 按实际成功的批量操作事件去重 | 次操作 |
| 批量退回影响 | 单独显示批量操作影响范围；期间作业数取并集 | 项作业；历史仅有计数时标为影响项次 |
| 我的质检待办 | 当前分配给本人的有效 PENDING 抽检项 | 项质检；可附作业去重数 |

“完成作业”原指标改名“制作提交作业”；新增“参与处理作业”作为覆盖制作与质检的总览。批量影响、快捷直放、废弃等专项处置单列，不加入逐项质检结论次数。

同一人对同一作业完成文案质检、图片质检及一次图片复检：参与处理作业为 1，质检完成作业为 1，文案质检结论为 1 次，图片质检结论为 2 次，其中复检 1 次。不同人员的作业去重数不能直接相加作为团队总量。

内容首轮通过率继续归制作提交人。质检人的通过/退回数量描述判定结果，不作为其准确率或绩效优劣；没有独立复核标注时，不展示“质检准确率”。

日期按北京时间：历史质检按结论提交时间，批量处置按操作时间，当前待办不受历史日期筛选影响。无有效样本的比率显示“—”；查询失败显示不可用，不冒充 0。

## 3. 页面调整

### 个人数据统计

1. 顶部显示“参与处理作业、制作提交作业、质检完成作业、质检结论次数”，所有卡片携带日期和指标条件下钻。
2. 增加“我的质检”区域：文案/图片待质检、待复检；历史文案/图片质检、通过/退回、复检、批量退回、专项处置。
3. 原“待质检”明确标为“我的内容等待质检”，与“需要我质检”分别展示。原制作待办及“我负责的/我创建的/与我相关”筛选仅作用于制作区。
4. 纯质检同学进入页面即可看到质检工作；同时承担制作与质检时，两类贡献都展示。展示依据为实际记录和能力，不只依赖 USER/REVIEWER 角色标签。
5. 每日趋势增加质检结论；质检历史独立列表显示匿名编号、阶段、结论、是否复检、操作时间。按照现有盲审和详情权限决定是否提供查看入口，不把质检历史强行接到普通任务详情。
6. 提交质检后触发统计刷新，沿用现有工作区刷新机制和失败保留旧数据的行为。

### 管理员统计

主看板人员来源改为：期间制作贡献账号、期间质检/处置操作账号、当前制作负责人、当前质检指派账号的并集。只有批量处置记录的人也必须可检索。

人员表提供“全部贡献 / 制作 / 质检”视图和独立排序。筛选“质检”按实际操作类型，不按账号角色；管理员和兼任人员都可以出现。默认总览按参与处理作业排序，质检视图可按质检结论次数排序；批量处置仅有操作、没有逐项结论时仍保留人员行。

| 人员 | 制作提交作业 | 文案质检 | 图片质检 | 其中复检 | 通过 / 退回 | 当前质检待办 |
| --- | --- | --- | --- | --- | --- | --- |
| 只做质检的同学 | 0 项 | 12 次 | 8 次 | 3 次 | 17 / 3 次 | 4 项 |

复检已包含在文案/图片质检内，上例总质检结论为 20 次。批量处置、专项处置放入人员详情和独立列选择，避免主表过宽。

团队新增“质检参与人数、质检完成作业、质检结论次数、当前质检待办”指标。下钻、趋势、搜索、人员详情和 CSV 导出全部使用同一成功报表的快照、日期与口径版本。

折叠的“生成与流程概况”保留当前生产责任视角，明确“参与负责人”只统计生产负责人，提供进入人员贡献/质检视图的入口，避免用户把它理解为完整团队工作量。

## 4. 数据实现

### 4.1 独立保留质检操作事实

不把原 QUALITY 的 account_id 改成质检人，否则会破坏现有制作质量统计。建议增加一张最小追加式事实表 `quality_review_activity_events`，与现有 operator_performance_events 一起进入共享报表快照。

核心字段：event_key、source_type、source_event_id、actor_account_id、actor_username_snapshot、actor_display_name_snapshot、stage、kind、occurred_at、task_id、sampling_item_id、freeze_id、sample_kind、outcome、details。

- kind 区分 QA_REVIEW、QA_BATCH_RETURN、QA_DIRECT_PASS、QA_DISCARD 等实际操作。
- 逐项事实必须有任务和抽检项；批量事实可以只有 freeze_id。现有 operator_performance_events.task_id 非空，不宜伪造一个任务代表整批操作。
- details 仅保存必要的版本引用、批次引用、原因、影响范围及来源精度，不保存生成正文、图片或凭据。
- 来源键唯一；必要时对逐项结论增加阶段 + 抽检项的唯一约束。同一源事件允许分别生成“新逐项结论”和“批量处置”，但二者使用不同键且只计入各自指标。
- 不随任务/账号删除级联清除；身份快照与账号 ID 保留，不能让同名新账号继承贡献。
- 在原业务事务写入源事件后追加，回滚不留下贡献。现有接口成功重放不重复计数。
- 按 actor_account_id、occurred_at 建查询索引，并为阶段、时间及来源键设计索引；按现有中心快照方式聚合，不从浏览器逐任务拉取。

逐项权威来源为 copy_sampling_events、image_sampling_events 的实际决策事件，actor_account_id 为实际执行人。不能直接统计 sampling_items.reviewed_by_account_id：批量操作会更新多个成员的这些字段，并不代表逐条检查过。

### 4.2 批量及特殊动作

| 场景 | 建议处理 |
| --- | --- |
| 普通 PASS / RETURN_SINGLE | 形成 1 次有效逐项质检结论；排除明确模拟、系统行为及自检 |
| 强制复检 | 新抽检项形成新的质检结论；不受内容首轮通过率排除规则影响 |
| 文案直接整批退回，触发项尚无结论 | 触发项计 1 次退回；批量退回计 1 次；其余成员仅计影响 |
| 文案触发项已单条退回后再整批退回 | 原逐项结论保留原操作人；新增批量操作归实际发起人，不再新增逐项结论 |
| 图片整批退回 | 当前事件没有逐项触发证据，只计 1 次批量操作及影响范围；不得按被更新的成员数补造质检次数 |
| 管理员快捷直放 | 记快捷处置工作量；不计普通质检和内容首轮通过率 |
| 图片质检废弃 | 根据源事件上下文确认是质检侧废弃后单列；生产负责人废弃不记为质检贡献 |
| 文案退回并建议废弃 | 逐项质检仍为退回；后续实际废弃属于另一次处置，不再次算质检 |
| 自动放行、未抽中、未操作、SUPERSEDE | 不形成质检工作量；版本后续失效不抹除已确认的历史结论 |

质检工作量的有效性函数与制作质量样本的有效性函数分别实现。不能直接复用现有质量排除标记：非首轮和强制复检虽不进入首轮通过率，却确实属于质检工作。

### 4.3 待办与接口

当前质检从 copy_sampling_items、image_sampling_items 按 assigned_review_account_id 读取。PENDING、选中、版本有效、账号能力、暂停/取消和自检限制与现有质检队列一致；“已分配但暂不可操作”的项单列阻塞，不混入“现在可处理”。统计查询本身不触发结批或状态变更。

个人接口增加 `contribution`、`qa`、`qaPending`、质检趋势和可用性状态。个人质检历史采用专门的只读分页接口或明确的新 mode；不复用当前只认识 COMPLETE/QUALITY 的历史分支。

管理员接口增加相同的质检指标、activity 类型筛选、排序与明细指标白名单。账号、阶段、批次、日期筛选必须覆盖两类事实，不能只在查询制作事实后用 reviewerId 临时拼人员。快照和导出保存完整成功范围及更新后的口径版本。

共享新增的 `src/quality-review-statistics.mjs` 负责质检分类、去重、汇总；个人与管理员服务共同调用。旧的内容质量聚合保持独立。数据量超过完整读取上限时明确提示缩小范围，不能返回截断总量。

### 4.4 历史回填

先按可信的源事件 ID、账号 ID、操作时间回填，再用来源键与实时采集去重。抽检项只作为补充上下文，不以当前任务负责人替代历史操作人。

源事件已删除时，可评估已保存的 QUALITY 事实中 reviewerId、samplingItemId 和原结论时间作为逐项记录补充；必须能够确认实际决策和排除快捷直放，且与源事件回填使用同一规范键。不能将缺少依据的数据按当前状态推测出来。

图片旧批量事件目前仅存 affectedCount 的情况，展示原记录的“影响项次”；没有可靠成员集合时，不声称能够计算历史影响作业去重数。新增批量事件保存必要成员引用以支持后续准确下钻。

记录历史覆盖起点、缺失身份、缺失时间及不可恢复条数。先在隔离备份上评估回填和索引耗时，再按部署流程升级；本方案不执行生产变更。

## 5. 实施顺序

| 阶段 | 交付内容 |
| --- | --- |
| 第一阶段：补齐记录 | 新增质检操作事实、来源幂等、历史回填、共享聚合；明确逐项/批量/特殊处置分类 |
| 第二阶段：两端同时接入 | 个人质检卡片与待办、管理员人员并集与质检视图；同步完成下钻、趋势、导出及字段说明 |
| 第三阶段：验证与升级准备 | 回归实际业务路径、核对个人与管理员同口径结果、检查盲审与账号权限、评估备份回填 |

主要涉及 `server/src/personal-workspace.mjs`、`src/personal-workspace.mjs`、`server/src/operator-performance.mjs`、`src/operator-performance.mjs`、两个页面及类型/详情组件，以及新迁移和质检事件采集。现有业务文件若有并行修改，实现时应合并处理，避免覆盖。

质检耗时可作为后续独立增强：只有掌握分配/改派的完整时段，才能按人计算周转时间。当前仅有分配时间不能还原历史有效处理时长，不在本轮补计工作量时推算“工时”。

## 6. 验收标准

1. 某同学未创建、未负责任何作业，仅完成文案质检 5 次、图片质检 3 次：个人显示 8 次，管理员可搜索到该同学，人数及导出一致。
2. 同一作业跨文案/图片/复检：作业数正确去重，质检结论次数按阶段和轮次保留。
3. A 制作、B 质检、C 后续接手：A 的制作贡献、B 的质检贡献不转给 C；C 只取得当前责任及自己之后的实际操作贡献。
4. 原提交人无首轮样本时通过率仍为“—”；不能拿本人质检别人的通过率冒充本人产出质量。
5. 文案整批退回分别覆盖新触发项、已经退回的触发项、此前已通过的非触发成员；图片批量退回不能生成逐项工作量。
6. 重复点击、request_id 重放、回填重跑、事务失败均不新增重复贡献；事件来源与汇总可核对。
7. 只获派质检待办但尚未提交、只做批量处置、管理员普通质检、快捷直放、质检废弃分别正确展示。
8. 删除任务、账号改名、账号删除及同名重建不转移历史；缺失身份明确标示。
9. 北京时间跨日、跨月、期间初审而次日复检、每日去重与期间去重差异均有验证。
10. 同一数据快照下个人卡片、管理员人员行、下钻和导出一致；盲审详情不泄露制作人或非授权任务内容。
11. 查询失败、报表过期、超量、历史缺失有明确状态；刷新不把不可用数据显示为 0。

自动化验证使用纯函数样例、假的接口、临时 PostgreSQL 与浏览器用例，不调用模型或消耗模型额度。本次只验证漏计原因并形成方案，尚未运行上述新增功能的验收测试。
