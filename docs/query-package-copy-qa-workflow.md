# Query 词包、文案抽检与交付流程（当前实现）

本文记录当前代码已经实现的业务边界。主流程为：

`Query 词包导入 → 人工筛选（通过即自动入队）→ AI 生成文案 → 分配审核负责人 → 人工初审 → 批次锁定/抽检（返工稿走强制复检）→ 待生图队列 → 生图 → 图文终审 → 交付池`

本流程止于交付资源准备与下载，**不包含任何平台发布、自动发布或生产排期能力**。

## 1. Query 词包筛选与自动入队

Query 词包使用独立的数据模型，不等同于生产任务。一个词包包含多条明细，每条明细分别保存校验状态、人工筛选结论和投产结果。

- 单次导入支持 1–10,000 条明细。系统按 500 条分块写入，校验空 Query、长度、任务输入和图片数量，并在同一词包内按“去空白、统一大小写”的 Query 标识识别重复项；当前粘贴导入界面会先合并本次输入中的重复行，服务端数据模型仍可明确记录 `DUPLICATE` 状态。
- 明细校验状态为 `READY`、`DUPLICATE`、`INVALID` 或 `TASK_CREATED`；人工筛选结论为 `PENDING`、`SELECTED` 或 `REJECTED`。两组状态分开记录，避免把“数据无效”和“人工不采用”混为一谈。
- 重复项和无效项在导入时直接标记为不可采用；有效项可直接在行内点击“通过/淘汰”暂存混合结论，再一次提交本批。勾选框仍保留给同结论批量处理，但不是逐条操作的前置步骤。每次提交保留实际筛选账号、事件与可选原因；详情默认只显示 `PENDING`，处理完成的行立即从当前列表隐藏，仍可切换到“已通过”“已淘汰”或“已创建作业”查看。
- 词包详情按筛选条件和搜索词在中心服务分页，每次最多返回 200 条，并使用“原始序号 + 明细 ID”游标连续读取。Web 端虚拟渲染当前视口附近的行，接近底部时自动加载下一批；筛选提交后重新读取当前条件的首批结果，不会反复传输整个词包。
- 管理员按待筛 Query 明细分配工作，可选择多名启用中的审核员或普通作业员并“一键平均分配”，也可给每人填写精确条数；按条数分配未覆盖的余量保持仅管理员可筛。重新分配只改变仍为 `PENDING` 的明细，不影响已提交结论或已创建作业。受派人只能列出相关词包并查看、筛选分给自己稳定账号 ID 与用户名的明细；不能看到其他人的 Query，也不能导入、废弃、永久删除或调用历史兼容投产接口。停用、改为管理员或删除账号会立即收回其剩余明细；管理员始终可访问全部词包。
- 新版筛选请求为每条明细携带 `expectedItemVersion`。不同人员同时提交互不重叠的 Query 时不会因词包总版本变化互相冲突；同一明细被重复提交或在页面打开后被重新分配时，服务端会拒绝旧版本并要求刷新。旧版只携带词包版本的调用仍保留用于同发布包兼容。
- 点击“通过”时，筛选结论、生产批次、正式任务及小红书检索绑定在同一数据库事务内完成。任务直接以未分配的 `COPY_QUEUED` 状态进入文案生成队列；点击“淘汰”不创建任务。任一步失败都会整体回滚。
- 每次通过操作形成一个生产批次，批量通过的多条 Query 属于同一批次。当前界面不再提供单独的“创建生产批次”步骤；显式投产接口仅用于兼容历史上已经 `SELECTED` 但尚未创建任务的明细。
- 每条词包明细最多创建一个任务；已创建任务的明细不能再次筛选或投产。文案生成完成、任务进入 `COPY_REVIEW_PENDING` 后，系统才通过自动派单池或管理员操作分配审核负责人。
- 创建后，任务和生产批次保存词包名称、外部编号及 Query 快照；即使以后永久删除原始词包，正式任务仍保留当时的词包名称。管理员任务工作台可按这份名称快照进行不区分大小写的模糊搜索；普通用户的任务响应、列表和详情均不返回或显示这些来源字段。后续抽检范围仍以生产批次为边界，不以整个原始词包为边界。

词包生命周期：

| 状态 | 含义 |
| --- | --- |
| `IMPORTED` | 已导入，尚未形成完整筛选结论 |
| `SCREENING` | 正在人工筛选，仍有有效明细待处理 |
| `READY` | 历史兼容状态：存在已通过但尚未自动创建任务的明细 |
| `PARTIALLY_USED` | 已创建至少一个任务，仍有有效明细待筛选或历史待创建明细 |
| `USED_UP` | 已通过的明细均已创建任务，且没有有效明细待筛选 |
| `ABANDONED` | 管理员明确放弃，或全部有效明细均被淘汰 |

## 2. 文案初审评分语义

初审分数评价的是 **AI 第一次生成的机器原稿**，不是人工修改后的最终稿：

| 机器原稿分数 | 当前处理规则 |
| --- | --- |
| 1 分 | 必须直接废弃任务，不能保存后继续修改或通过 |
| 2 分 / 2.5 分 | 必须实际修改标题、正文或标签；机器原稿不能直接放行 |
| 3 分 | 唯一可在不修改文案时直接确认通过的机器原稿分数 |

图片文案规划的调整与机器原稿分数分开处理，单独修改规划不算“文案已修改”，不能满足 2 分或 2.5 分原稿的文案返修要求。

系统同时保留机器原稿的原始评分、扣分原因和备注。2 分或 2.5 分原稿经人工实际修改并确认达标后，系统将修改后的最终版本记录为 3 分；界面不要求用户再次给修改稿打分，也不会用最终 3 分覆盖原稿评分事实。这里的“提交审核结果”只完成文案初审：普通生产批次仍可能先进入抽检，不等同于立即开始生图。

## 3. 批次闭合、范围锁定与精确抽检

生产批次中的任务在初审通过后先进入 `COPY_QC_PENDING`，不会由较早完成的任务提前流向生图。只有当该批次全部成员均为“最终人工通过”或“已废弃”时，批次才闭合：

- 抽检总体只包含最终人工通过的当前文案版本；1 分废弃项及其他已废弃任务不进入抽检总体。
- 抽检关闭时，整个批次直接统一放行到 `IMAGE_QUEUED`。
- 抽检开启时，系统在批次闭合这一刻读取比例与盲评配置并生成不可变冻结快照。抽中和未抽中的任务都继续处于等待状态，直到该批抽检得出处理结果。

### 3.1 精确样本数

设符合条件的总体数量为 `N`，管理员配置的比例为 `rateBps`（0–10,000，分别对应 0%–100%，精度 0.01%）：

`Q = rateBps 为 0 时取 0，否则取 ceil(N × rateBps / 10,000)`

因此，非零比例对非空总体至少抽中 1 条；比例为 0 时样本数为 0，冻结后立即放行。

### 3.2 按最终通过人分层（Hamilton 最大余数法）

系统按最终人工通过人的稳定账号 ID 分层。设某层人数为 `nᵢ`：

1. 该层理论份额为 `nᵢ × Q / N`。
2. 先给每层分配理论份额的整数部分。
3. 剩余名额按小数余数从大到小依次补齐，即 Hamilton 最大余数法。
4. 余数相同时，使用“算法版本 + 冻结种子 + 账号 ID”的 SHA-256 结果稳定排序。

算法不强制“每位通过人至少抽 1 条”，小样本下某一层配额可以为 0，但全批最终抽样数始终精确等于 `Q`。

### 3.3 层内稳定选择与快照

每层内使用 SHA-256 稳定排序，输入包含算法版本、冻结种子、任务 ID、文案修订 ID、人工通过事件 ID 和文案内容哈希，然后取该层配额内的前若干条。

冻结记录会保存配置版本、比例、种子、算法版本、盲评策略、总体数、样本数、每层配额、快照哈希，以及所有抽中和未抽中成员的版本与排序证据。刷新页面不会重抽，后续配置变化也不会改变已冻结批次。

## 4. 单条打回、整批打回与放行

“发现一条错误”默认只处理该条，不会自动触发整批打回。

### 单条打回

- 管理员和质检员始终可以打回当前待检错误项，与“质检员整批打回”开关无关。
- 必须填写至少一个原因或备注，并校验当前文案内容指纹，避免对已经变化的版本提交结论。
- 仅错误项回到 `COPY_REVIEW_PENDING`，同批其他任务继续保持冻结。
- 单条打回后，管理员或质检员可执行独立的“放行同批其余”操作；系统不会把被打回且尚未通过强制复检的任务一并放行。

### 整批打回

- 管理员始终具有整批打回权限；质检员只有在管理员开关当前为开启状态时才能执行。权限在提交事务内再次实时校验，开关被关闭后，旧页面不能继续提交。
- 整批打回是显式高风险操作，不由单条失败自动执行。提交前必须读取影响范围预览，提供完整成员清单、确认数量、原因说明和请求标识。
- 必须指定一个随机抽中的错误项作为触发项；可以从当前待审样本直接发起，也可以先单条打回、确认问题后再显式升级为整批打回。质检员不能以自己最终通过的文案作为触发项。
- 服务端锁定冻结批次，逐项核对成员、状态、版本与内容哈希；范围变化时拒绝提交并要求重新预览。
- 触发错误项记为 `RETURNED`，同批其他受影响项记为 `BATCH_AFFECTED`。如果触发项此前已经单条打回，升级整批时不会再次修改其版本或重复累计错误；统计中只有真实错误触发项计为抽检错误，其他成员只计“整批受影响”。

当所有随机样本均通过时，系统自动将该冻结批次的抽中和未抽中成员统一放行到生图阶段。

## 5. 盲评边界

盲评策略在批次冻结时写入快照，仅对质检员生效；管理员仍可查看来源信息。质检员的盲评响应采用服务端字段白名单，只提供：

- 匿名质检编号和匿名批次编号；
- 当前最终通过稿的标题、正文、标签和图片文案规划；
- 内容指纹/版本令牌及允许执行的质检动作。

盲评时不返回 Query、真实任务 ID、真实生产批次 ID、词包名称、创建人/负责人/最终通过人身份、原评分、扣分原因或历史记录。处于有效盲评冻结中的任务，质检员也不能通过通用任务详情或资产入口绕过匿名队列；猜测任务 ID 时按不存在处理。

管理员查看非盲抽检队列时可以按词包名称跨页筛选，并在列表与详情中看到词包来源；该筛选能力不向独立盲评响应开放，质检员的匿名字段白名单保持不变。

质检员不能审核自己最终通过的文案，该判断使用稳定账号 ID，而不是可能重复使用的用户名。

## 6. 强制复检

以下文案返修在重新通过后必须进入 100% 单条强制复检，不受普通抽检总开关或比例影响：

- 文案抽检的单条打回或整批受影响返修；
- 图文终审选择“退回文案”或“文案、图片都退回”。

返修必须真实修改标题、正文或标签；仅保存、仅改规划或原样通过都会被拒绝。人工确认返工稿达标后，系统将最终稿记录为 3 分并创建独立的 `MANDATORY_RECHECK` 复检轮次，不重新抽签，也不混入普通随机首检正确率。提交返工稿不会立即生图；只有强制复检通过后，任务才会进入待生图队列，并继续释放满足条件的原冻结批次。

## 7. 图文终审与交付池

图片评分与文案机器原稿的通过规则不同：图片仍以高于 2 分为通过门槛，`2.5` 分或 `3` 分可通过，`1` 分或 `2` 分只能重试或废弃。

图片生成完成后的 `MANUAL_ARCHIVE` 在界面中显示为“图文终审”。管理员或质检员可以执行五种业务动作：

| 动作 | 后续状态与处理 |
| --- | --- |
| 终审通过 | 任务进入 `REVIEWED`（界面显示“交付池”），创建与当前文案版本、当前图片版本绑定的 `READY` 交付条目 |
| 退回文案 | 回到 `COPY_REVIEW_PENDING`，完成真实文案修改后强制复检 |
| 退回图片 | 回到 `IMAGE_QUEUED`，重新生成图片 |
| 文案、图片都退回 | 先回到文案返修，文案通过强制复检后再进入生图 |
| 废弃 | 任务进入 `CANCELLED` |

交付池只列出 `REVIEWED` 且存在当前 `READY` 交付条目的任务，并要求交付条目绑定的文案修订和图片运行仍与任务当前版本一致。终审通过写入 `READY` 前，还会在同一数据库事务内确认当前文案可归档、图片结果非空，且每个选定图片资产都属于当前任务和当前图片运行；不完整结果会回滚终审提交，不会留下一条只能看到却无法下载的交付记录。交付池列表、词包聚合筛选、单条资源包下载和批量导出均只对管理员开放。普通作业员和质检员不获得交付池数据或下载能力。终审后再次修改图片或发起返工时，旧的 `READY` 交付条目会被撤回。

管理员有两个相互独立的集中下载入口：

- “批量下载”只导出当前明确勾选的条目，页面搜索和词包筛选不会清除其他已勾选项；单次最多勾选 200 条。列表每次读取 200 条，超过后可继续“加载更多”，后续条目仍可搜索、分批勾选和逐条下载。
- 预览上传支持两种明确范围：勾选词包后按上限整包上传尚未上传项，或在交付表格中勾选具体任务后精确上传这些条目。精确上传不会用同词包的其他内容补位；提交时同时校验任务 ID、词包归属、READY 状态、预览状态和当前交付版本，范围变化时要求刷新重选。
- 未勾选条目时，选择词包会导出该词包在中心服务中的完整 `READY` 快照；未选择词包则导出全部可交付项。这两种完整快照都不使用浏览器当前页的任务 ID，因此不受当前展示条数和旧版 20 条批量上限影响，也不会因为本地关键词搜索而漏项。指定词包没有可交付项时明确失败，不会回退成全池导出。
- 批量 ZIP 按安全清洗后的词包名称建立一级目录，历史无词包任务统一进入“未归属词包”；清洗后重名会自动增加编号，不能形成路径穿越。单任务资源包和指定词包导出的下载文件名也携带词包名称。Excel 第一列固定为“词包名称”，后续保留 Query、完整文章、链接和图片列，词包名按普通文本写入。
- 服务端只加载当前任务的交付元数据，逐项写入支持 ZIP64 的外层归档，并在准备完成及真正下载前用同一数据库快照批量复核全部版本绑定；准备完成后签发绑定当前管理员、五分钟有效的一次性凭证，由浏览器原生流式下载，避免把完整 ZIP 缓存在页面内存。HEAD 探测不会消耗凭证，准备阶段断线会取消任务并清理临时文件，进程重启遗留的临时目录也会定期清扫。失败时不会返回部分 ZIP。

同一管理员同一时间只允许一个“正在准备、等待下载或正在传输”的交付包，中心服务全局最多同时处理两个交付导出，避免通过慢下载或重复点击堆积大文件。正在传输的包每收到数据就续期；连续 5 分钟没有任何传输进度时会自动中止并回收。进程关闭也会中止仍在准备或传输的包，并等待临时文件清理完成。界面代理与部署路由的准备时限统一为 60 分钟；真正的凭证下载不设置额外的应用层绝对时长，但仍受无进度保护、实际部署平台和网络连接限制。

## 9. 管理员开关及生效时点

当前管理端提供文案抽检相关的流程开关和抽检比例。数据库中仍保留旧版“作业员导入词包”字段以兼容已部署数据，但它不再授予普通用户权限，界面也不再展示该开关。

| 配置 | 作用 | 生效时点 |
| --- | --- | --- |
| 启用文案抽检 | 决定闭合的生产批次是创建冻结快照还是直接放行 | 生产批次闭合时读取 |
| 抽检比例 | 0–100%，精度 0.01% | 与批次冻结快照一起锁定 |
| 启用独立盲评 | 决定质检员是否看到来源身份信息 | 与批次冻结快照一起锁定 |
| 允许质检员整批打回 | 只控制质检员的整批打回；不影响单条打回和“放行同批其余” | 预览和提交时实时校验，提交事务内复核 |

配置使用版本号做并发保护，管理员基于旧版本保存时会收到冲突提示，避免覆盖其他管理员刚刚完成的修改。抽检种子和算法版本由系统保存，不在当前界面中开放随意修改。

## 10. 幂等、审计与永久删除边界

- 词包创建、明细分配、筛选（含同事务自动创建任务）、历史兼容投产、放弃和永久删除，以及抽检冻结、通过、单条打回、整批打回和异常放行，均使用 `requestId + 操作指纹` 做幂等保护。同一请求可安全重试；相同 `requestId` 携带不同内容会被拒绝。
- 新版 Web 在提交明细分配和按明细版本筛选前要求中心 `/health` 报告 `queryPackageVersion >= 4`；旧中心、缺少版本或无法确认版本时直接停止操作，不能出现界面与中心权限或并发语义不一致的混合版本结果。历史兼容词包写入仍保留各自的 V2/V3 门槛。
- 文案和图文审核使用审核会话及请求指纹防止重复提交；关键变更在数据库事务和行锁内完成，并校验版本或内容指纹。
- 抽检保存冻结、通过、单条打回、整批打回、放行事件；整批事件额外保存触发项、影响项、成员哈希和冻结快照哈希。随机首检统计按最终通过人的稳定账号 ID 汇总，只用已得出结论的 `PASSED/RETURNED` 计算正确率；待检项不进分母，强制复检和整批受影响数单独统计。
- Query 词包永久删除仅管理员可执行，且仅限 `USED_UP` 或 `ABANDONED`。操作前提供影响预览，并要求当前版本、精确输入词包名称、删除密码、原因和请求标识。
- 永久删除会删除词包主数据、明细、筛选事件及包含词包内容的旧请求快照；已经投产的任务和生产批次不删除，外键解除后仍保留必要的业务来源快照。
- 永久删除审计仅保留已删除词包 ID、明细数、脱离词包的任务数、操作者、原因、请求标识和时间，不保留 Query、输入、文件名或明细内容。为网络重试保留的删除回执同样不含业务内容。
