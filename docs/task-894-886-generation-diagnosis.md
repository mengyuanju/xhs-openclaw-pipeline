## 为什么重试仍会失败

`src/codex-app-server.mjs` 的计时器从启动 app-server 子进程就开始计时。启动、连接重试、模型准备、原生生图等待和回合完成共享同一个预算。先前的独立 `PLANNING` 调用不占该次生图预算，但生图调用内部的准备过程会占用。因此错误中的“300 秒”不等于图像工具实际获得了 300 秒。

配置默认值是 `src/model-api-config.mjs` 的 `DEFAULT_IMAGE_TIMEOUT_MS=300000`；这几轮快照中的 `modelApi.imageTimeoutMs` 均为空，实际失败耗时也都约 300 秒。四次超时调用的许可排队只有 10–14 毫秒，没有本地排队占用大部分预算的证据。

同一时段 #927、#774、#736、#784 也出现了 300 秒图片调用超时，分布在 haimo1 和 haimo2。这支持生成连接或响应时延是共性问题，不能只把失败归因于这两条 Query 的内容；仍不能据此确认是哪一层网络或远端服务故障。

三次超时都有 `failed to refresh available models: timeout waiting for child process to exit`。两次 #894 另有 `patch rejected: empty patch`，但其后原生生图已正常启动；这些是伴随异常，现有证据不足以认定为最终失败原因。

两条任务每一轮的 `image_production_chain_id` 均不同，快照没有 `imageResume`，并且重新调用视觉规划与首图生成。记录显示这些轮次是重新生图，没有复用前轮已完成页面的检查点。超时本身不会触发应用自动重试；执行机对 `CODEX_EXEC_TIMEOUT` 明确设置 `autoRetry=false`。

页面上的 99% 来自 `src/standalone-image-generation.mjs` 失败分支的固定值，不能解释为图片已经完成 99%。首图超时轮次的生成和验收计数为零，与实际未收到首图完成事件一致。

## #886 最新失败暴露的结果保留问题

`src/codex-app-server.mjs` 收到原生图片 `item/completed` 时，只把候选结果暂存在内存 `items` 中；直到 `turn/completed` 才将其输出到标准化事件。统一计时器到期会终止进程，返回超时，不会把这些候选作为已完成结果交给上层。

`src/codex.mjs` 对超时直接抛错，不会继续验证和复制该图片。检查点要等图片调用成功返回后才能登记。因此，最新轮次中已经回传保存信息的第 3 页没有进入正常产物和检查点，最终任务仍显示已完成 2 张。

已用纯内存 fake 子进程复现这一边界：先返回原生图片完成消息，随后不返回回合完成，达到截止时间后仍得到 `CODEX_EXEC_TIMEOUT`，标准化输出没有图片候选；大体积图片数据还会挤掉原始协议头部。这次验证没有调用真实模型，也没有修改源代码。

恢复程序当前只扫描任务目录中的固定候选文件，不会自动从执行机全局 `generated_images` 发现这类文件。若 haimo2 的声明路径仍有有效 PNG，可以核验后追回；不能直接把声明路径当成已成功的交付结果。

## 处理方向

1. 核对 haimo1/haimo2 到 Codex 的连接、代理和超时日志，以及 haimo1 在 16:14–16:16 的执行器退出或重启记录，分别解决连接重连和心跳中断。
2. 图片等待应获得独立预算，并保留总截止时间、原生结果核验和本地进程清理。短期可以评估将已有 `imageTimeoutMs` 调至 450000–540000；当前校验允许最多 540000，但延长等待不能修复连接中断，也不保证远端结果返回。此次没有修改配置。
3. 有完整检查点时使用原执行机续跑，减少整套重新生成。#886 首轮已有三页通过验收，但中心尚无上传资产；能否续跑要核对 haimo1 的本地检查点与文件完整性。不能把已失联的远端结果直接当成成功。
4. 修复原生结果保留：图片完成事件应立即保存结构化候选信息和诊断，并进入现有路径、字节与图片质量核验；回合结束超时时仍应允许按已核验候选恢复。日志应移除图片 Base64 后再限长，保留完整事件边界。不能靠伪造 `turn/completed` 或跳过验收把任务标为成功。
