## 修复结果

| 类别与代表任务 | 本地确认的原因 | 本轮处理 | 验证边界 |
| --- | --- | --- | --- |
| #483：竹垫子放真皮沙发上可否 | `searchEvidence` 把 commentary 和 final_answer 合并，污染有效 JSON | 优先取最后一条明确 final_answer；仅在没有明确终稿时兼容最后一条无 phase 的旧协议消息；不合并 commentary/reasoning | 用精简协议响应复现先失败后通过；没有重发原 Query 到真实模型 |

| #434：驾驰火花塞 各型号 优缺点及真实评价 | 将页面“核对5项”的结构数量误当作外部事实 | 对清单页标题/副标题的“核对/检查 N 项”，逐次验证本页 N 个不同非空条目；仅豁免该数字出现位置 | 预检和最终视觉规划校验复用同一规则，避免通过预检后再次被拦 |

| #466/#465/#490：案例匹配超时/TLS | 运行时异常被当作无效评分，立即重复调用，最后包装为“评分不完整” | 已识别的 Codex 运行时错误直接透传，保留原码、诊断及停机属性 | 格式修复和上下文拆批仍保留；超时/TLS 不自动重放结果未知的调用 |
| 各阶段 at capacity | 原错误归为通用 EXEC_FAILED，缺少容量分类和共享冷却 | 新增 MODEL_AT_CAPACITY，与 quota 分开；同一执行主机共享约 60–65 秒冷却 | 冷却不等于提供方恢复，也不是跨主机全局限流；分布式失败任务仍保守等待人工续跑 |
| TLS / 本地超时 | TLS 缺少专用码；重连事件可能抢占实际超时诊断 | 新增 TRANSPORT_FAILED；本地超时时保留 EXEC_TIMEOUT；成功重连后仍可接受新终稿 | 鉴权/额度耗尽继续暂停；不自动切换模型，不把过载解释为账户额度耗尽 |

DeepSeek 官方说明：Responses API 无状态，搜索记录原样回传可恢复结果；`tool_choice=none` 可停止工具调用；服务端搜索自动续推最多 10 轮。因此无终稿与搜索轮次边界有关是合理推测，尚不是这 8 条故障的已证实上游根因。[官方协议文档](https://api-docs.deepseek.com/zh-cn/guides/responses_api/)

- 最终测试：主项目 **1,014 项通过**，中心服务 **169 项通过**，合计 **1,183 项，0 失败、0 跳过**；类型检查、生产构建和 mock smoke 均通过。最后一次新增超时关联回归后已重跑主项目完整测试与生产构建。

## 远程后续操作

1. 中心服务、前端和执行机同步本轮代码版本。需要更新的进程包含中心服务、Next.js 网页及使用 Codex/DeepSeek 的执行机；只更新网页不能修复模型解析或失败字段保存。本轮没有数据库结构迁移。
2. 先选 #483、1 条无终稿、1 条 JSON 格式错误进行小批量验证。成功标准：有效终稿一次通过；异常搜索最多一次整理；链路显示原失败和整理结果；仍缺证据时阻断文案。
3. #434 从已有文案重新进行图片预检；#467 先依据招聘公告补足证据或删除不支持的年限，再提交图片流程。
4. 对容量不足，等待供给恢复或人工切换可用模型后再续跑。若多执行机共用同一账户/上游，应协调并发；本地主机冷却不能替代跨主机协调。
5. 对超时/TLS/质检失败，先核对最新执行和检查点。已有成功图片时使用“从失败步骤续跑”，不直接整单重生成；缺失检查点时保留人工处理。
6. #437 的任务级质检错误与可见调用不完整对应、#402/#398 的最新运行与旧错误是否同步，仍需远程版本和对应执行日志进一步核验。本轮没有把这些未证实情形宣称为已修复。

验收时分别确认“程序缺陷修复”和“上游模型调用恢复”。离线测试可证明前者的回归行为；后者必须由更新后的真实调用轨迹确认。
